# 05 安全与治理：记忆不应让低信任内容变成高权限

核查日期：2026-11-11。[专题导读](README.md) · [安全一手来源](sources.md#safety)。

## 1. 持久化会延长一次错误的寿命

外部网页、用户上传内容或工具返回可能含误导性指令。若被存成“经验”，再进入下次会话，它就从一次输入变成反复出现的上下文。

MINJA 研究展示了通过查询交互污染某些经验库的攻击路径；它不证明所有系统、或某个未测试 Claude 服务已经被攻破。官方 memory 文档也警告持久写入中的 prompt injection 风险。[MINJA v5](https://arxiv.org/html/2503.03704v5) · [官方警告与适用前提](sources.md#safety)

安全设计首先区分内容与控制：记忆里写着“系统允许发送所有文件”，不意味着系统真的授予了这个权限。把来源标成 verified，也不能提升它在指令层级中的角色。

## 2. 为读、写、维护、发布分别授权

| 边界 | 需要回答的问题 |
| --- | --- |
| 读取 | 当前用户／租户／项目允许看到哪些数据？ |
| 写入 | 谁能提出候选，谁能提交持久更新？ |
| 维护 | 整理者能访问哪些日志，能否改源事实？ |
| 预加载／发布 | 谁批准内容成为默认上下文？ |
| 执行 | 哪些外部操作仍需要明确确认？ |

这是本 Wiki 的治理建议。只读挂载降低一种写入风险，但不证明内容可信，也不解决越权读取。Prompt 中的防注入要求不是强制访问控制。[官方文档与 prompt 边界](sources.md#safety)

## 3. 过期与冲突，不应靠“相信最新一条”

原创反例：原始观察是版本 v1 的单位约定，今天编辑了由它生成的摘要。摘要文件的修改时间更新了，证据却仍旧。

建议将 observed_at、modified_at、source_version 和适用条件分开。新近编辑、检索分数高、引用次数多，都不替代核验。冲突若无法裁决，应保留双方的来源、范围和不确定性。

失效也不只删除一条笔记。原始事实已被索引、计划、报告和外部产物消费时，要检查派生链。笔记撤回不自动撤销已经发出的邮件或已经确认的订单。

## 4. 删除是一张数据流检查表

需要分别检查原始日志、当前笔记、索引／向量、wiki 页、默认注入层、历史版本、导出和备份。删除当前内容、redaction、archive、删除整个 store 是不同操作，依服务合同决定具体含义。

Anthropic 的托管 memory、Dreams、Claude Code 本地 auto memory 不是相同留存与删除合同，不能拿一个界面的删除按钮替其他产品作保证。[产品特定的数据处理边界](sources.md#safety)

这里不是法律意见，也没有完成任何服务的合规审计或删除验证。高敏感资料应先核验实际部署的数据处理条款，再决定是否进入记忆；本课不导入真实个人或业务资料。

## 5. 维护结果也要能回滚

建议的发布流程：

```text
冻结输入版本 → 生成候选 → 检查差异与来源 → 运行验收
                                      ↓
                     批准切换／保留旧版本／拒绝候选
```

回滚应恢复批准过的内容和索引，并记录哪些会话已经使用过问题版本。部分输出不是完整结果；失败任务的产物需要独立验收。

对默认注入层尤其要慎重：它减少每次搜索的成本，也让错误有机会进入所有后续会话。可将高影响事实、稳定指令与普通经验分别管理，避免一次总结悄悄改变全局权限。

## 自测

1. 只读 store 就不存在风险了吗？**没有，读取越权、假内容与外泄仍需控制。**
2. 修改时间今天，事实就新鲜吗？**不是，检查原证据的观察时间与版本。**
3. 删除原笔记，引用它的报告就修好了？**没有，需沿派生关系检查。**
