# 03 表示与检索：索引帮助找到证据，不代替证据

核查日期：2026-11-11。[专题导读](README.md) · [四层来源](sources.md#architecture)。

## 1. 四种表示各解决一个问题

| 表示 | 用途 | 需要保留的边界 |
| --- | --- | --- |
| 原始事件／会话记录 | 回查当时看到什么、做了什么 | 冗长、含错误观察或敏感内容 |
| 记忆笔记 | 留下规则、偏好、未完成事项 | 摘要可能丢条件或混入推断 |
| Wiki／实体页／任务页 | 连接跨文档事实与来源 | 链接会悬空、页面会重复、更新会滞后 |
| 预加载索引／高层上下文 | 启动时告诉 agent 知道什么、去哪里找 | 占预算；错误可能进入每次会话 |

这张表以原文层级为入口，但用途与失败检查是教学解释。原文讨论 wiki 与搜索互补，也展示 wiki 无明显收益和比原文还大的情况，不能直接推出“wiki 一定优于检索”。[案例与协议边界](sources.md#evaluation)

## 2. 一个索引应让你知道去哪里查

原创项目记忆树：

```text
index：当前目标、适用范围、重要入口
├─ decisions：决策、理由、批准者与版本
├─ verified-rules：可重现的操作规则与测试证据
├─ tasks：待办、完成回执、阻塞与依赖
└─ source-links：原始资料和待核验争议
```

这是一个可选组织，不是行业统一目录结构。索引不应把所有细节复制一遍；来源事实需回到各页，并继续能到原证据。一个清楚的入口比一张没有版本和来源的巨大汇总表更容易核验。

对时间敏感事实，记录观察时刻和有效条件。对精确条款、单位、配置等细节，区分引用与摘要；不要让“更简洁”变成丢掉否定词或例外条件。

## 3. 检索有三道不同的筛选

原创的安全阅读路径：

```text
权限／范围过滤 → 内容相关性检索 → 适用性与证据复核 → 任务中的采纳
```

语义相似度可用于找到候选，却不提供租户授权、时间有效性或事实验证。直接将“最相似的 top-k”交给执行者，会把搜索成功与行动许可混在一起。

可以结合全文搜索、结构字段、向量相似度和显式链接，但各自有盲区：关键词遗漏近义表达，向量可能混淆数值／否定，结构字段依赖标注，链接依赖维护。选择应根据具体查询做实验，而不是先认定某个数据库品牌就是记忆架构。

召回后仍要问：源版本是否变了？当前问题是否与当时条件相同？用户的新指令是否覆盖历史默认？[记忆到执行的分析](../deep-learning/openmoss/06-agent-memory-and-executable-evaluation.md)解释为何 recall 与任务收益可能不共同排序。

## 4. 预加载是一笔固定开销

把一条规则预装进每次会话，会让模型不必先意识到要查它；同时它消耗所有会话的预算，也扩大错误传播的频率。

原创预算算例：索引 600 个假想 token，另外三条笔记分别 900、500、300；本次记忆预算 1,400。若索引必须加载，只剩 800，可以选 500＋300，不能塞入 900。数字是教学设定，不是实际 tokenizer 的计数。

更大的窗口不是权限或事实质量的替代品。也不能由某条笔记进入窗口，推出模型必定遵循它。Claude Code 的具体注入限制属于该产品，不是所有 harness 的共同硬上限。[产品特定机制](sources.md#safety)

## 5. Wiki＋原始检索怎样减少两种损失？

索引／wiki 帮助发现多个相关来源与概念关系；原始搜索提供精确内容与新的证据。二者组合可以避免两种问题：

- 只有原文搜索：每题重新发现同一条跨文档关系。
- 只有摘要表示：复用旧结论，却找不到它的例外、来源或新版本。

这是作用机制的假设，需要在当前语料和任务上测量。构建 wiki 的额外计算及更新成本也要计入；不能只报告在线省下的 token。[成本台账](sources.md#cost)

## 自测

1. 向量相似度很高，就可跨租户读取吗？**不可以，权限不是排序分数。**
2. Wiki 比原文大一定更好吗？**不是，先检查是否真正降低查找成本和保留必要证据。**
3. 本次预算剩 800，能加入一条 900 的记忆吗？**不能；也不能偷偷改变分母说预算够用。**
