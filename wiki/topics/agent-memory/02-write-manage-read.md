# 02 写入、维护与读取：把记忆当作有版本的状态

核查日期：2026-11-11。[专题导读](README.md) · [官方机制与版本](sources.md#provenance)。

## 1. 三种操作，不是一条摘要命令

| 操作视角，属于本 Wiki 的教学组织 | 主要问题 | 典型失败 |
| --- | --- | --- |
| 写入 | 哪些观察值得留下，依据是什么？ | 保存猜测、重复写短命状态 |
| 维护 | 怎样核验、去重、修正、建链接和失效？ | 摘要丢条件、并发覆盖、错误升级 |
| 读取 | 当前任务需要什么，允许读什么？ | 漏召回、召回过多、跨范围泄漏 |

Anthropic 原文的 dreaming 跨越这些维护工作，并不是只把日志变短。其公开 wiki 示例分别组织分析与整理角色；这些 prompt 是行为建议，不是事务执行器。[公开机制核验](sources.md#provenance)

## 2. 在线记录与离线整理怎样接力？

原创设计：

```text
任务中：保存少量原始观察与候选笔记
                  ↓
维护中：回查证据、处理冲突、生成索引／表示
                  ↓
审阅后：发布一个新的可用版本，后续会话按需读取
```

在线写入使刚发现的信息能立即被后续任务使用，却会占用注意力与工具调用；离线整理能集中处理跨会话模式，但其输出可能晚于下次请求。

调度建议不是“每条日志都做 dreaming”。可以按访问频率、版本变化、冲突、风险与预算决定复核优先级。一次维护应记录输入版本、产出版本、核验范围、失败与成本，而不只保存一个“整理完成”标志。

## 3. 比较原证据，不是比较两份摘要

假想例：笔记 A 和笔记 B 都说“接口自动转换单位”，它们却来自同一条未经核验的助手猜测。两份笔记不是两个独立证据；合并后写“多次确认”反而扩大错误。

建议维护时保留：

- 原始证据与派生关系；
- 已核验事实与待测假设；
- 旧值、新值及各自适用范围；
- 无法裁决时的冲突状态，而不是强行选一个流畅版本。

删除原笔记不能自动修复已引用它的索引、计划和报告。失效应沿派生关系传播，再复核受影响产物。可在[离线实验](lab.md)观察一个三层依赖图的失效。

## 4. 两个 writer 怎样丢掉一条好记忆？

以下是原创的顺序交错模拟：

| 时刻 | Writer A | Writer B | 文件状态 |
| --- | --- | --- | --- |
| 1 | 读版本 0 | 读版本 0 | 原有事实 α |
| 2 | 增加事实 β，写回 | 仍持有旧副本 | α、β |
| 3 | 已完成 | 增加事实 γ，整体覆盖 | α、γ；β 丢失 |

两个 writer 的事实都可能正确，仍然因为更新方式丢写。官方托管 memory 文档提供内容 hash 前置条件，用于发现读写冲突；公开 quickstart 也说明共享页仍可能丢失写入。[官方并发语义与局限](sources.md#provenance)

本 Wiki 的教学 CAS（compare-and-swap）要求“只有当前版本仍等于我读到的版本，才接受替换”。B 的旧版本写入被拒绝，重新读取后再合并。但 CAS 只检测冲突，不能判断 β 与 γ 在业务上是否矛盾。

高争用页面可以分拆为单来源／单实体页面，由单独整理步骤建立索引；需要精确文字的任务应避免只保留丢失条件的共享汇总。这是设计建议，不是证明某个实现已经零丢写。

## 5. 原地改写与产生新版本，安全性不同

原文中的 dreaming 是一般过程；当前 Dreams 产品的 copy-on-output、自编 cookbook 更新指定 store，是不同接口合同。不能因为名字相同就假定输入一定不改、输出一定完整或会自动替换线上记忆。[三种 dreaming 语境](sources.md#provenance)

建议采用“候选产出 → 差异审阅 → 验收 → 显式切换”的发布路径。保留旧版本便于回滚，但旧版本有敏感数据时，又必须明确其删除和留存策略。

## 自测

1. 两条相互引用的摘要算两个独立证据吗？**先检查共同祖先，引用数量不代表独立性。**
2. CAS 写入成功证明事实正确了吗？**没有，它只处理一种并发条件。**
3. 维护任务失败后已有输出 ID，就算完成了吗？**不算，要按具体服务的终止状态与产出合同检查。**
