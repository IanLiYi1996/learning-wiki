## 怎么读：不要先背一堆币名

## 1. 先认识账本：数字钱为什么不能像照片一样复制

一本账本记录“谁拥有多少、哪些转移已经发生”。银行存款、平台余额、游戏积分，都可以通过数据库记录。转账时，系统调整余额或记录一笔新的变动。

普通文件可以复制：把照片同时发给两个人，不会少一张。钱不能这样处理。若小林只有一份资产，却同时支付给小周和小陈，这叫**双花**：同一份可支配价值被重复花费。

中心化系统由经营者决定哪笔支付先成立。Bitcoin 尝试解决的另一种问题是：没有一个统一的记账机构，彼此不完全信任的人能否共同核对支付历史？

难点不只是复制账本。即使大家都保存一份账，也可能先收到不同交易；恶意参与者还可以运行许多假身份。系统因此必须同时回答：

1. 谁有权花这份资产？
2. 两笔冲突支付，哪笔进入共同认可的历史？
3. 为什么伪造大量身份不能轻易夺取决定权？
4. 参与记账和验证的人，为什么愿意持续付出成本？

这四个问题，分别把我们带向签名、共识、抗女巫攻击和经济激励。**区块链不是“不需要信任”，而是重新安排信任和验证的对象。**

依据：[Bitcoin 白皮书第 1–5 节](https://bitcoin.org/bitcoin.pdf)。更深入见 [系统模型与信任边界](chapters/01-system-model.md)。

## 2. 区块、链、状态分别是什么

**交易**是改变账本的请求，例如“小林把某份资产支付给小周”。**区块**把一批交易及必要的协议数据组织起来。一个区块通常通过哈希引用前一个区块，于是形成按协议连接的历史。

哈希可以先理解为数据的指纹，下一节会解释。Bitcoin 的区块头还包含交易集合的 Merkle 根：把交易标识按树形反复组合、哈希，得到一个摘要。它帮助验证某笔交易是否被区块承诺；摘要不是全部交易内容，也不能单独证明交易有效。

**历史**是“发生过什么”，**状态**是“按认可的历史执行后，现在能花什么、账户有哪些值”。Bitcoin 主要维护未花费输出集合；Ethereum 还维护账户、合约代码和存储状态。保存一个摘要，不等于拥有重建状态所需的全部数据。

最容易误解的是“不可篡改”：

- 改一笔旧记录，会改变相应摘要，需要重新满足后续共识条件。
- 但短期分支竞争、重组、软件漏洞和参与者集中仍然可能影响历史稳定性。
- 链只能验证协议允许验证的东西。写入“这箱货是真品”，不会自动证明实物真的是真品。

所以“上链”首先是**记录与验证方式**，不是对现实事实的自动背书。

公链通常允许公众参与；许可链限制参与者及身份。两者适合不同信任模型。不是所有区块链都需要公开交易的币，也不是所有系统都用挖矿：Hyperledger Fabric 就不要求用原生加密货币支付挖矿激励。

依据：[Bitcoin 区块链指南](https://developer.bitcoin.org/devguide/block_chain.html)、[Ethereum 状态结构](https://ethereum.org/developers/docs/data-structures-and-encoding/patricia-merkle-trie/)、[Fabric 的许可模型与无原生币设计](https://hyperledger-fabric.readthedocs.io/en/latest/whatis.html)。

## 3. Bitcoin、BTC、区块链、代币不是同一件东西

**区块链**是一类系统设计；**Bitcoin**是其中一个具体网络与协议；**BTC**是这个网络里的原生计价单位。

一枚 BTC 不是存放在手机中的“币文件”。它体现为账本里的金额，以及谁能满足相应花费条件。拷贝钱包文件可能复制了控制这些金额的密钥，却不会把链上金额翻倍。

先用这张表区分常见对象：

| 对象 | 例子或形态 | 实际表达什么 |
| --- | --- | --- |
| 原生币 | BTC、ETH | 由链协议直接记账的资产；作用因链而异 |
| 同质化代币 | ERC-20 代币 | 某个合约或代币程序定义的数量记录 |
| 稳定币 | USDC 等 | 追求某种价格锚定的资产；需要另查支撑及兑付机制 |
| NFT | ERC-721 的某个 tokenId | 同一合约中可区分的独特编号及控制关系 |
| 凭证或份额 | vault shares、LP 份额 | 对另一套资产或策略的权益记录，不必等于底层资产数量 |
| 平台余额 | 交易所显示的 BTC | 平台账内的客户权益，不等于你直接控制同额链上 UTXO |

“原生币/代币”区分技术实现；“稳定币/NFT/治理代币”描述用途或属性，它们不是互斥的分类轴。一个稳定币也可以是 ERC-20 代币。

同名不等于同资产。资产身份至少要标清：**哪条网络、哪个合约或 Mint、哪个资产编号**。伪造者也能发行名叫 USDC 的代币。技术上能发行，不等于具备储备、赎回权或市场需求。

币价也不是协议输出的“正确答案”。稀缺性、用途、流动性、供需和预期可能影响交易价格，但“总量有限”本身不保证有人买、不保证价格上涨。

依据：[Bitcoin 交易与余额模型](https://developer.bitcoin.org/devguide/transactions.html)、[ERC-20](https://eips.ethereum.org/EIPS/eip-20)、[ERC-721](https://eips.ethereum.org/EIPS/eip-721)、[ERC-4626 份额](https://eips.ethereum.org/EIPS/eip-4626)、[Circle USDC 条款](https://www.circle.com/legal/usdc-terms)。最后一段是区分技术属性与价格结论的风险判断，不是估值模型。

## 4. 密码学入门：哈希、加密和签名各做一件不同的事

**哈希**把输入数据计算成固定长度的摘要。同一输入、同一算法，结果相同；稍微修改输入，结果通常会明显变化。它不是把数据加密后等待“解密”，也不能靠哈希恢复原文。

**加密**主要保护内容的保密性：没有适当密钥的人不应读懂内容。**数字签名**主要证明某个控制者授权了某条消息，并帮助发现消息被修改。

Bitcoin 挖矿主要用双 SHA-256 计算区块头哈希；Bitcoin 的花费授权则使用相应脚本和签名规则，传统路径常见 ECDSA，Taproot 使用 BIP340 Schnorr。不要把“挖矿算哈希”理解为“破解用户私钥”。

**私钥**是需要保密的签名材料；**公钥**可用于验证相应签名。知道公钥，在合理密码学假设下不能有效反推出私钥。**地址**是用于指定收款条件的编码，生成方式因链和地址类型而异；它不是所有链统一的“公钥直接打印出来”。

小林向小周付款时：

1. 钱包构造要授权的交易消息。
2. 用小林控制的签名材料生成签名。
3. 节点验证消息及花费条件，而不需要获得小林的私钥。

签名合法证明的是授权关系，不证明小周守信，也不证明合约安全。合法签名可以授权一笔对签名者很不利的操作。

依据：[Bitcoin 签名与支付脚本](https://developer.bitcoin.org/devguide/transactions.html)、[BIP340](https://github.com/bitcoin/bips/blob/master/bip-0340.mediawiki)、[Bitcoin 区块头结构](https://developer.bitcoin.org/reference/block_chain.html)、[Ethereum 账户与密钥](https://ethereum.org/developers/docs/accounts/)。实际签名消息的编码另见 [Bitcoin 工程章](chapters/02-bitcoin.md)，不是对交易截图或 txid 随便签一下。

## 5. 钱包到底装了什么，丢了手机会怎样

钱包主要是**管理控制材料、构造签名、查询账本和展示资产的工具**。链上的资产不会因为你卸载 App 就消失；但如果所有控制及恢复材料都丢了，通常也不会有一个总管理员替你重置。

**助记词**是某些钱包采用的恢复材料编码。BIP39 方案从助记词和可选 passphrase 推导 seed，再配合派生规则生成密钥。它不是“每条链的登录密码”，也不是所有钱包唯一的恢复方式。

需要分清三个容易混淆的密码：

- App 密码：通常保护设备上的本地访问或文件。
- 助记词：可能恢复整组密钥；泄露后往往足以失去控制。
- BIP39 passphrase：参与生成 seed；不同 passphrase 对应不同钱包，忘记后不能靠同一助记词自动找回原钱包。

恢复还可能需要派生路径、地址/脚本类型、多签其他参与者或合约恢复配置。“记了几个单词”不等于验证过完整恢复方案。

**热钱包**的签名环境在线或经常连接；**冷钱包**尽量隔离签名材料；**硬件钱包**把签名边界放在专用设备中。它们不是三个互斥标签，也不是绝对安全等级。硬件钱包不能替你识别所有恶意交易；签错目标仍然可能造成损失。

**自托管**通常由你控制密钥或授权策略；**托管**通常由平台控制链上资金，你通过平台账号请求转移。自托管减少对托管方的依赖，同时把备份和授权责任交给自己。多签、MPC、智能账户又会改变谁能授权及如何恢复，必须逐条看权限路径。

依据：[Bitcoin 钱包指南](https://developer.bitcoin.org/devguide/wallets.html)、[BIP39](https://github.com/bitcoin/bips/blob/master/bip-0039.mediawiki)、[BIP32](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki)、[Safe 账户权限](https://docs.safe.global/advanced/smart-account-concepts)。深入见 [密钥与账户安全](chapters/06-security.md)。

## 6. 谁在运行网络：节点、矿工、验证者、RPC

**节点**是运行协议软件、连接网络的计算机或服务。全节点独立检查它认可的交易和区块规则；它不是因为计算机名字叫“全节点”就自动诚实。

**矿工**参与 PoW 出块竞争；**验证者**在 PoS 等协议中参与提议、投票或形成证据。它们可能同时运行节点，但角色不能混为一谈：验证规则与争取出块权是不同工作。

**RPC**是应用向节点或服务发请求的接口。钱包常经 RPC 查余额、估费、广播交易，因此“资产自托管”不代表“每项数据都是自己独立验证的”。界面、节点服务和索引都可能有故障、延迟或错误。

为什么不是“一台电脑一票”？因为创建身份很便宜。攻击者可以伪装成大量参与者，称为**女巫攻击**。不同共识机制通过不同稀缺资源或身份规则限制这种能力：

- **PoW，工作量证明**：用满足条件的计算结果表达出块竞争成本。
- **PoS，权益证明**：按质押及协议规则分配参与权，并通过惩罚或其他机制约束行为。
- **许可身份机制**：事先限定谁能参与，并明确组织治理与责任。

Ethereum 已使用 PoS；不是还在用显卡挖 ETH。PoS 也不是“存钱后自动得到无风险利息”：验证者有运行职责，惩罚、退出及委托风险因机制而异。不同 PoS 网络的阈值、最终性和处罚不能互相照搬。

依据：[Bitcoin P2P 与节点](https://developer.bitcoin.org/devguide/p2p_network.html)、[Ethereum PoS](https://ethereum.org/developers/docs/consensus-mechanisms/pos/)、[Fabric 许可模型](https://hyperledger-fabric.readthedocs.io/en/latest/whatis.html)。Ethereum 模型是具体例子，不是所有 PoS 链的统一定义。

## 7. Bitcoin 里的币：UTXO 与找零

Bitcoin 的常规付款不是简单修改一张“地址余额表”，而是消耗旧输出、创建新输出。**UTXO**全称 Unspent Transaction Output，意为“还没有被花掉的交易输出”。

一个输出带有金额和花费条件。钱包显示的余额，是它认为自己能控制的相关未花费输出的合计；一个输出不一定只是“一个人一把私钥”，还可能有更复杂条件。

假设小林控制一个 **0.10 BTC** 的 UTXO，想付给小周 **0.03 BTC**。教学交易可以这样安排：

```text
输入：引用旧交易中的 0.1000 BTC 输出

输出 1：0.0300 BTC → 小周的收款条件
输出 2：0.0699 BTC → 小林的找零条件
差额：  0.0001 BTC → 本交易手续费

0.1000 = 0.0300 + 0.0699 + 0.0001
```

旧 UTXO 被完整消耗，不能留一部分继续花。找零通过**新的输出**回到小林控制的条件；如果没有找零输出，未分配给输出的剩余金额可能成为手续费。

输入里的 **outpoint**用“旧交易标识 + 输出编号”指定到底花哪一笔输出。小林如果又构造一笔花同一 outpoint 的交易，两笔可能各自签名合法，但不能在同一条有效历史中都花掉这个输出。

**1 BTC = 100,000,000 satoshi（聪）**。钱包工程按最小单位整数计算，避免小数误差。手续费主要与交易占用资源和当时需求有关，不是固定按转账金额抽成。

依据：[Bitcoin 交易指南](https://developer.bitcoin.org/devguide/transactions.html)、[支付与手续费指南](https://developer.bitcoin.org/devguide/payment_processing.html)。算例是人为设置，不是当前费率或推荐付款方案。

## 8. 挖矿到底在挖什么，为什么会有不合格候选区块

挖矿不是从硬盘里挖出已有的币，而是**竞争提出一个满足工作量证明条件的新区块**。

矿工准备候选区块：挑选交易、放入领取奖励的 coinbase 交易，并形成区块头。区块头包含前一区块哈希、交易摘要、时间、目标值编码 `nBits` 和可调整的 `nonce` 等数据。

然后不断尝试：

```text
准备候选区块及区块头
  → 改变 nonce 等允许变化的数据
  → 计算区块头双 SHA-256
  → 把哈希当作数值，与目标值比较
  → 不满足：继续尝试
  → 满足：向网络提交，由其他节点完整验证
```

合格的 PoW 条件是：

```text
区块头哈希的数值 ≤ 目标值 target
```

教学时假设哈希只在 `0000–9999` 之间，目标是 `0009`。这不是真实 SHA-256，只用于理解筛选：

| 这次尝试的结果 | 是否满足目标 | 接下来 |
| --- | --- | --- |
| 5732 | 否 | 改输入再试 |
| 6801 | 否 | 改输入再试 |
| 0007 | 是 | 提交候选，等待其他规则验证及链选择 |

若这些结果近似均匀，只有 10 个值符合目标，单次命中概率约千分之一；平均尝试次数不是“第 1000 次必定成功”。

关键是：**交易内容合法，不等于区块头哈希满足 PoW。**候选区块可以装着完全合法的交易，却暂时没有足够小的哈希。这些失败是计算搜索的正常结果，不是软件出错。

同一输入再算不会得到新结果。矿工必须改变输入；nonce 用完还可调整 coinbase 中的额外数据，改变交易摘要等，扩大搜索空间。真实哈希有 256 位，所谓“前面很多个零”只是小数值在特定表示下的直观现象，规则本质仍是数值比较。

还要分清三类失败：

1. PoW 未命中：通常不会当作已挖出的块广播。
2. PoW 命中，但包含非法交易或超额奖励：全节点拒绝。
3. PoW 和内容都有效，但另一个分支胜出：未进入当前活动链，通常称 stale block。

依据：[Bitcoin 挖矿指南](https://developer.bitcoin.org/devguide/mining.html)、[区块头参考](https://developer.bitcoin.org/reference/block_chain.html)、[Core v30.0 的 `CheckProofOfWorkImpl`](https://github.com/bitcoin/bitcoin/blob/v30.0/src/pow.cpp)、[区块内容验证](https://github.com/bitcoin/bitcoin/blob/v30.0/src/validation.cpp)。v30.0 在这里是固定源码核验基线，不是最新安装版本建议。

## 9. 目标值由谁规定，谁能改变规则

要分开“**制定算法**”和“**计算此刻的数值**”。

Bitcoin 主网的算法和参数属于共识规则，历史上由软件设计建立，并由选择运行兼容规则的参与者维护。每个全节点根据已有区块及同一算法，独立计算下一块应该使用的目标值。没有一个中央“难度服务器”给所有人发目标。

矿工把目标值的压缩编码 `nBits`写入候选区块头；节点既检查它是否符合应有目标，也检查哈希是否满足它。矿工不能把目标改大、让挖矿更容易，然后指望其他节点照单全收。

主网按区块高度**每 2016 个区块**调整一次，目标平均间隔为 **600 秒，即 10 分钟**，名义周期约两周。10 分钟是设计目标，不是每块精确倒计时；不是墙钟刚好过两周就触发调整。

忽略整数及压缩编码细节，方向可以这样记：

```text
新 target ≈ 旧 target × 实际时间跨度 / 预期时间跨度
难度 difficulty 与 target 大致成反比

出块太快 → target 变小 → 合格范围缩小 → 难度提高
出块太慢 → target 变大 → 合格范围扩大 → 难度降低
```

假设上个周期只用约 7 天，新目标大约减半、难度大约翻倍。实际算法有调整限幅和目标上限；上一周期首尾 2016 块只有 2015 个间隔，计算分母仍按 `2016 × 600`。这是实现细节，不影响上述方向。

谁改得了规则？开发者可以提议和发布软件，参与者可以选择运行版本；但一份提案、一位开发者或多数矿工，都不能自动迫使运行旧规则的节点接受它认为非法的区块。

**软分叉**通常收紧原有有效集合；**硬分叉**涉及不向后兼容的规则变化，可能造成网络分离。实际激活、兼容与治理过程要看具体升级。“去中心化”不等于没人协调，也不等于所有意见都能无成本兼容。

依据：[主网参数](https://github.com/bitcoin/bitcoin/blob/v30.0/src/kernel/chainparams.cpp)、[目标调整实现](https://github.com/bitcoin/bitcoin/blob/v30.0/src/pow.cpp)、[`bad-diffbits` 独立检查](https://github.com/bitcoin/bitcoin/blob/v30.0/src/validation.cpp)、[Bitcoin FAQ 的控制与升级说明](https://bitcoin.org/en/faq)。这里只讲主网，测试网/regtest 的例外不照搬。

## 10. 新币从哪来，矿工拿到什么

Bitcoin 区块的第一笔特殊交易叫 **coinbase transaction**；这里是协议术语，不是指名为 Coinbase 的公司。

它允许矿工在协议上限内领取：

```text
区块奖励上限 = 该高度允许的新发行补贴 + 区块内已有币支付的交易手续费
```

补贴是新增发行，手续费是既有资产的转移。矿工不能想写多少就写多少；即使 PoW 合格，超额领取仍会被全节点拒绝。coinbase 输出也有成熟期限制，不能像普通收款一样立即花费。

主网初始补贴为每块 50 BTC，每 210,000 块减半，通常约四年，但不是按固定日历日期。补贴序列是 `50 → 25 → 12.5 → 6.25 → 3.125 → …`，按最小单位及整数规则逐渐降至零；常说总量上限约 2100 万 BTC。

总量上限不等于所有币都可流通：丢失密钥、不可花费输出等，会让部分已发行金额无法被正常支配。供应规则也不保证价格。

矿工的收入不是净利润。设备、电力、运维、融资、停机、矿池结算及币价都会影响结果。矿池把参与者的算力组织起来，并用通常比主网更容易的 **share**目标衡量贡献；矿池认可一个 share，不代表它挖出了主网区块。

因此不要把“挖矿奖励”“DeFi 流动性挖矿”“做任务领币”混成同一件事。后两者往往指应用层分发激励，不是 Bitcoin 的 PoW。

依据：[补贴与奖励检查源码](https://github.com/bitcoin/bitcoin/blob/v30.0/src/validation.cpp)、[减半主网参数](https://github.com/bitcoin/bitcoin/blob/v30.0/src/kernel/chainparams.cpp)、[coinbase 与成熟期](https://developer.bitcoin.org/devguide/block_chain.html)、[矿池与 shares](https://developer.bitcoin.org/devguide/mining.html)。本节不估算当前挖矿收益。

## 11. 一笔转账什么时候才算完成

现在把小林的 BTC 转账串起来：

```text
选 UTXO、构造金额/找零/费用
  → 小林授权签名
  → 广播给节点
  → 某些节点收入自己的待处理池
  → 矿工将其放入有效区块
  → 区块进入当前认可的链
  → 后续区块累积确认
  → 收款方按自身风险规则入账
```

**mempool，内存池/待处理池**是节点的本地候选交易集合，不是全网唯一队列。节点可能有不同中继策略、交易视图或接收顺序；也不是所有链、所有发送路径都必须经过公开 mempool。

**广播成功**不等于被包含；**被包含**不等于永远不会重组；应用显示的**已到账**还可能包含平台自己的风控、确认和内部记账。

BTC 交易所在区块算第 1 次确认，后面每接一个活动链区块再加一次。更多确认通常降低相应威胁模型下的重组风险，但“6 确认”是常见业务阈值示例，不是不可撤回的宇宙定律。

**重组 reorg**是节点切换到另一条认可历史的过程。Bitcoin 先检查有效性，再在有效候选链中选择最大累计工作量的链；不能只数区块。被移出的付款可能重新进入候选集，也可能因为冲突而不再成立。

**最终性 finality**是协议对历史稳定性的保证机制。PoW 的确认通常是概率性；某些 PoS 协议可用投票证据定义最终性，仍有故障假设，且“最终确认了失败交易”不代表付款成功。

多数算力攻击主要可能影响顺序、重组、双花和审查，不能凭算力伪造他人签名、任意花别人的 UTXO 或让原规则节点接受超额发行。

遇到广播超时，正确的第一问题是“原交易到底有没有被接收或包含”，不是“赶快签第二笔”。超时只是没有取得确定回复；重新构造付款可能造成重复。

依据：[Bitcoin P2P 传播](https://developer.bitcoin.org/devguide/p2p_network.html)、[链与分支](https://developer.bitcoin.org/devguide/block_chain.html)、[累计工作量实现](https://github.com/bitcoin/bitcoin/blob/v30.0/src/chain.cpp)、[Ethereum PoS 最终性](https://ethereum.org/developers/docs/consensus-mechanisms/pos/)。超时处理是由广播不确定性推导的工程建议，详见 [钱包状态机](chapters/05-wallet-engineering.md)。

## 12. Ethereum：从付款账本到可编程状态

Bitcoin 也有脚本和复杂花费条件，不是“完全没有程序”。Ethereum 的区别在于提供通用智能合约执行环境，让交易可以调用程序、修改合约状态，而不只是支付原生币。

**ETH**是原生资产；**EVM，Ethereum Virtual Machine**是执行合约字节码的虚拟机规则；**Solidity**是常用合约语言之一。网络、币、运行时和编程语言是四层，不是四个同义词。

Ethereum 主要使用账户模型。账户包含余额、nonce、代码/存储相关承诺等；代币余额则由相应合约维护，不等于账户的原生 ETH 余额。

**nonce**可以理解为某个发送账户的交易序号。它帮助约束顺序和重复执行，不是 Bitcoin 挖矿区块头里的同名尝试数。两笔不同交易可以竞争同一个账户 nonce，但不能在同一有效历史中都把它当独立支付执行。

**Gas**衡量执行资源，**gas price**是每单位资源的价格，**gas limit**是这笔交易允许使用的上限。Gas 不是一种叫“汽油币”的资产。

对普通 EIP-1559 类型交易，可用下面的教学假设：

```text
假设小林给未委托、无代码的小周账户转 ETH：
gasUsed = 21,000
baseFee = 8 gwei/gas
有效 priorityFee = 1 gwei/gas
手续费 = 21,000 × 9 = 189,000 gwei = 0.000189 ETH

1 gwei = 10^(-9) ETH
```

实际有效小费受费用上限等约束；`gas limit × maxFeePerGas`不是最终一定扣走的金额。基础费销毁，小费按协议给出块相关参与者。涉及合约、7702 委托或额外数据的转账，不能默认只消耗 21,000 gas；blob 等还有独立费用机制。

交易执行失败（**revert，回退**）时，普通业务状态变更通常回滚，已执行消耗的费用仍然支付，已纳入区块的发送方 nonce 仍被消耗。未通过基本检查、根本没入块的请求不能混为“失败也扣钱”。7702 的授权处理还有单独的持久性例外，见下一节。

小林转一个 ERC-20 稳定币给小周时，常规交易的链上 `to`是代币合约，`data`编码函数及收款参数；小周是合约调用里的收款对象。不能只看最外层 `to`和 ETH `value`来判断谁收到代币。

依据：[Ethereum 账户](https://ethereum.org/developers/docs/accounts/)、[交易](https://ethereum.org/developers/docs/transactions/)、[Gas](https://ethereum.org/developers/docs/gas/)、[EIP-1559](https://eips.ethereum.org/EIPS/eip-1559)、[ERC-20](https://eips.ethereum.org/EIPS/eip-20)。深入见 [状态与执行](chapters/03-ethereum.md)。

## 13. 智能合约：代码、权限和外部信息

**智能合约**是按链的执行规则运行的程序及其状态。“智能”不保证它聪明、安全或公平；“合约”也不自动等于一份法律上可执行的合同。

**DApp，去中心化应用**通常包括网页/App、钱包、节点访问、合约及可能的后端。把一个环节放上链，不代表网页、域名、管理员、数据源和客服全部去中心化。

合约通常在被交易调用时执行，也可经其他合约调用；它不会因为墙上时钟到点就自己醒来。定时功能需要有人或自动化服务提交调用，另有链级特殊机制时要具体说明。

读合约交互时，先认识四个对象：

- **ABI**：描述如何编码函数调用、返回值和事件的接口格式。
- **事件/日志**：执行中按接口产生的记录，便于索引；不等于独立验证过全部业务结果。
- **状态**：程序存储的数值，例如余额和额度。
- **管理员/升级权**：可能改变规则或暂停功能的控制路径。

“已部署代码不能随便改”不等于“这个产品永远不能升级”。**代理合约 proxy**可让同一个入口地址使用新的实现逻辑；管理员、治理或模块可能改变实际权限。评估安全时要看是谁能升级、多久通知、能否暂停和是否有其他入口。

**Approve，代币额度授权**允许某个 spender 按合约规则动用一定额度；它不是立刻转账，但可能给后续转移建立权限。**Permit**可通过签名设置授权，不一定由用户自己发送设置交易。断开网页连接不自动撤销链上授权。

**账户抽象 AA**把签名验证、支付费用、恢复和批处理等能力做得更可编程。ERC-4337 的 UserOperation/EntryPoint 与 EIP-7702 的账户代码委托不是同一机制。7702 委托可持久存在，相关执行回退不自动撤销已经处理的委托；不能当作一次性“登录签名”。

**预言机 oracle**把价格、天气或其他外部数据提供给链上程序。合约不能凭空知道真实世界的价格；数据源、更新频率、异常处理与操纵成本都成为新的信任边界。

依据：[智能合约介绍](https://ethereum.org/developers/docs/smart-contracts/)、[Solidity ABI](https://docs.soliditylang.org/en/latest/abi-spec.html)、[代理槽位规范](https://eips.ethereum.org/EIPS/eip-1967)、[ERC-2612](https://eips.ethereum.org/EIPS/eip-2612)、[ERC-4337](https://eips.ethereum.org/EIPS/eip-4337)、[EIP-7702](https://eips.ethereum.org/EIPS/eip-7702)、[预言机](https://ethereum.org/developers/docs/oracles/)。新版钱包完整流程见 [Ethereum 升级教程](upgrades/01-ethereum.md)。

## 14. 代币、NFT、DAO：技术接口不决定经济权利

**同质化**表示同一资产类别里，等量单位通常可替换；**非同质化**表示要区分具体编号。例如一份 ERC-721 NFT 由网络、合约地址和 tokenId 共同标识。

NFT 的编号或所有者记录可以在链上，图片和描述可能在服务器或其他存储系统里。买到一个 token，不会由 ERC-721 标准自动获得作品版权、永久图片托管或法定收益权；需要另外查许可、权利安排和存储方式。这是标准范围的限制，不是在此判断某个作品的法律归属。

**DAO，去中心化自治组织**通常把提案、投票或执行的部分环节交给合约与治理机制。仍要问：谁能提案，票权是否集中，谁掌握多签，投票能否真正执行，管理员能否绕过。

**治理代币**可能给投票权；**业务收入**可能归运营公司或合约；**代币持有人收益**则需要独立机制。三者不能只凭项目名关联。治理代币不是自动拥有公司股权。

认识 **tokenomics，代币经济设计**，先看发行、增发/销毁权限、团队/投资者分配、锁定与解锁、费用流向和实际权利。所谓“销毁”，通常减少某种供应口径，不等于必然提高价格；“解锁”意味着转让限制改变，不等于马上实际卖出。

本节的检查框架是学习用分析方法，不是收益预测。能写一个代币合约，只证明能创建这些记录；商业需求、经济权利与合规仍是其他问题。

依据：[ERC-20 的接口范围](https://eips.ethereum.org/EIPS/eip-20)、[ERC-721 的编号与元数据接口](https://eips.ethereum.org/EIPS/eip-721)、[Ethereum DAO 介绍](https://ethereum.org/dao/)。检查具体产品时仍需它自己的权限、发行及权利文件。

## 15. CeFi 与 DeFi：买卖和流动性怎么发生

**CeFi，中心化金融服务**由平台经营者管理订单、托管和内部账；**DeFi，去中心化金融**把某些交易、借贷或结算规则交给合约。它不是“没有任何中心化依赖”的保证。

**CEX**是中心化交易所，常在平台内部撮合并记账；买入平台显示的 BTC 不代表每次都有一笔 BTC 链上转账。**DEX**是通过链上协议交换资产的交易场所，但其网页或其他组件仍可能有中心化控制。

**订单簿**记录买卖报价；**AMM，自动做市商**用池中资产和定价规则提供交易。不是所有 DEX 都用 AMM，也不是所有 AMM 都是同一个公式。

为了理解最简单的恒定乘积模型，假设池里有 `x`份资产 A、`y`份资产 B，规则近似为：

```text
x × y = k
```

小林把 A 放入池、换出 B，池子的比例变化，边际报价也变化。**流动性**是可交易资金和市场承接能力；它不是“总市值”的同义词。

**价格影响**是自己的交易改变池子价格的影响；**滑点**是报价到实际成交之间的差异。滑点容忍度是保护约束，不是单独一项固定收费；设得很宽可能让不利成交或攻击更容易。

**LP，流动性提供者**出资进入池，获取相应份额或头寸，并可能收取交易费。LP 面临相对单纯持有资产的组合偏离损失，俗称“无常损失”；退出时可以实现在账面上，名字不表示最终一定消失。

**MEV，最大可提取价值**来自交易排序、插入或排除等带来的机会，例如套利、清算或夹击。对用户而言，公开交易意图与宽松成交约束可能增加不利排序的风险。它不是单纯“矿工偷走 gas”。

多跳兑换、聚合器、集中流动性、v4 hooks 等会增加路径和规则；不能拿 `x × y = k`推断所有真实交易。现在先把“谁提供资金、谁定价、谁收费、谁能拿走资产”讲清楚。

依据：[Uniswap AMM 基础](https://developers.uniswap.org/docs/get-started/concepts/how-uniswap-works)、[v2 LP 收益与损失](https://developers.uniswap.org/docs/protocols/v2/concepts/understanding-returns)、[MEV](https://ethereum.org/developers/docs/mev/)。恒定乘积是教学模型，不是全部当前版本的完整实现。

## 16. 借贷、质押、收益：钱到底从哪里来

链上借贷常见流程是：小林提供抵押物，按协议额度借出另一种资产。若抵押价值下降或债务增加，抵押覆盖不足，可能发生**清算**：由协议允许的参与者还部分债并取得相应抵押物及激励。

**LTV，贷款价值比**是借款与抵押价值的比例；**清算阈值**是另一个触发风险处置的参数。不能把最大可借比例当安全保证。

假设仅有一种抵押物，价值 1000 个计价单位，清算阈值 80%，债务 600。采用 Aave 式教学口径：

```text
健康因子 = 抵押价值 × 清算阈值 / 债务价值
初始：1000 × 0.80 / 600 ≈ 1.33
抵押跌到 700：700 × 0.80 / 600 ≈ 0.93
```

低于 1 表示进入可清算风险区间；实际处置还受协议模式、参数、价格数据及版本规则约束。本算例不是某个真实资产的当前参数，也不是“1.33 就安全”的建议。

**Staking，协议质押**是参与某些共识或安全服务，不等于任何产品写“质押”就是共识质押。**流动性质押凭证**再把质押权益表达为可持有/转移的资产，增加运营方、合约、赎回队列和市场价格风险。

**再质押 restaking**把相关资产或安全承诺用于更多服务；不同产品可能增加额外处罚、依赖和退出条件。不能只看“复用资金”而不看追加的责任。

**收益金库 vault**把资金交给某个策略，用户收到 shares（份额）。shares 与底层 assets（资产）的换算可以变化；100 份金库份额不一定能取回 100 单位底层资产。ERC-4626 标准化接口，不保证策略盈利或随时足额退出。

所谓“收益”至少可能来自借款人利息、交易费、验证者奖励、链外资产收入，或新发行代币补贴。**APR**是不按再投入复利计算的年化表示，**APY**考虑相应复利假设；显示值不等于未来保证。

判断收益的四个问题：谁实际付钱？用什么资产支付？本金承担什么损失？停止奖励后业务还能否成立？如果答不出，就还没有理解产品。

**闪电贷**通常是在同一交易内按条件借出并归还的机制；若没有满足还款等条件，交易回退。某些接口还允许在符合抵押/信用授权等条件时转为债务头寸，必须看具体规则。它可以用于套利或其他原子操作，也可能放大已有设计漏洞，并不是能免费借钱不还。

依据：[Aave 健康因子与清算](https://aave.com/help/borrowing/liquidations)、[Ethereum 质押](https://ethereum.org/staking/)、[ERC-4626](https://eips.ethereum.org/EIPS/eip-4626)、[Aave 闪电贷](https://aave.com/docs/aave-v3/guides/flash-loans)。再质押及收益四问是风险分类框架，不对任何具体产品的收益或处罚参数作承诺。

## 17. 稳定币：稳定的是目标，不是无风险身份

稳定币追求相对美元等参照物维持价格。需要分开三个东西：**市场交易价、发行方赎回规则、储备/抵押能否支持兑付**。

| 常见机制 | 靠什么支撑 | 主要追问 |
| --- | --- | --- |
| 法币/资产储备支持 | 发行方持有的现金及其他允许资产 | 谁持有、报告是哪天、谁能赎回、是否可暂停或冻结 |
| 加密资产抵押 | 合约中的抵押及清算机制 | 抵押质量、价格源、清算深度、治理与链外敞口 |
| 对冲/合成机制 | 资产与对冲头寸、托管和交易基础设施 | 基差、资金费率、交易对手、保证金和赎回 |
| 反身性/算法机制 | 用相关代币与激励试图维护锚定 | 信心下跌时机制是否还能提供可兑现价值 |

真实产品可能混合这些机制，分类不是安全排名。不要把所有稳定币概括为“银行里一美元，链上一枚币”。

对于 USDC、USDT：

- 储备类型与披露范围要看各自发行方，而不是互相套用。
- 在交易所卖给别人，与直接向发行方赎回，是两条不同路径。
- 直接赎回资格、身份核验、地区、最低额度和暂停规则可能不同。
- 储备鉴证与公司财务审计不是同一件事；链上余额也无法独立证明链外全部储备。
- 发行方支持的原生版本，与第三方包装/桥接版本，不必有相同兑付关系。

对小林来说，“给小周转 100 个稳定币”和“让小周银行账户收到 100 美元”中间可能还隔着平台兑换、身份检查、费用、银行清算与工作日。

**脱锚 depeg**是价格偏离参照目标；**冻结**可能限制某个地址操作；**赎回暂停**影响法币兑现；**桥故障**影响另一条链上凭证的退出。它们不是同一类故障，不能都叫“链坏了”。

USDS/DAI、USDe、sUSDS/sUSDe 还要分别看治理、支撑机制与份额；名字相近不等于同一种资产。完整机制见 [稳定币升级教程](upgrades/04-stablecoins.md)。

依据：[Circle 透明度](https://www.circle.com/transparency)、[USDC 条款，注意其适用地域](https://www.circle.com/legal/usdc-terms)、[Tether 条款](https://tether.to/en/legal/)、[Ethena 机制](https://docs.ethena.fi/overview/how-usde-works.md)、[资金费率风险](https://docs.ethena.fi/protocol-overview/risks/funding-risk.md)。条款许可的资产类别不代表当前实际配置；本文不填即时储备比例或收益。

## 18. 为什么这么多链：扩容、L2、侧链和桥

如果每个验证者都要重复处理和核对工作，提高吞吐会给带宽、存储、计算与普通参与者的可负担性带来压力。扩容不只是“服务器加机器”，还要保持谁能验证、发生故障时谁能退出。

**L1，第一层**是提供基础共识的链；**L2，第二层**把部分执行移到其他系统，同时用设计中的基础层机制提供结算等保证。叫 L2 不证明安全模型完整。

**Rollup**批量处理交易，再向基础链提交相关数据和状态承诺：

- **Optimistic rollup**依赖相应争议/欺诈证明机制，挑战和退出有自己的时间及权限条件。
- **Validity/ZK rollup**提交执行有效性的密码学证明；证明哪些关系，取决于具体验证规则。
- **Validium**把数据可用性放在基础链之外，增加不同的数据依赖。
- **侧链 sidechain**有自己的共识，不能因为“能桥到 Ethereum”就自动继承 Ethereum 全部安全。

理解这些方案，要拆出三件事：**执行**算出新状态，**数据可用性 DA**让验证/恢复所需数据能被取得，**结算**决定哪个状态承诺被最终接受。证明执行正确，不等于数据永远可下载；数据可用，也不等于业务本身公平。

**Sequencer，排序器**负责某些系统的交易排序或快速接收。它给出的快速确认不自动等于基础链最终结算；如果停机，还要看替代排序、强制包含和退出是否真能用。

**桥 bridge**传递跨系统消息或资产权益，常见有锁定后铸造包装凭证、销毁后跨链铸造、用流动性完成转移等。资产不是穿过网线自动变成“同一枚文件”。

```text
小林在链 A 操作
  → 谁证明/认可 A 上的事件？
  → 谁把消息送到 B？
  → B 上谁验证、铸造或释放资产？
  → 哪条规则处理失败、重放、超时和退款？
```

**Wrapped，包装资产**通常代表对底层资产的某种权利；它增加托管、桥或合约边界。IBC 等互操作协议关注通信验证，不表示所有连接链自动共享同一验证者安全。

另外，“ZK”在扩容语境常强调有效性证明，**不自动意味着交易隐私**。很多 ZK rollup 的交易数据仍公开。隐私功能必须单独核验。

依据：[Optimistic rollups](https://ethereum.org/developers/docs/scaling/optimistic-rollups/)、[ZK rollups 与 validium](https://ethereum.org/developers/docs/scaling/zk-rollups/)、[侧链](https://ethereum.org/developers/docs/scaling/sidechains/)、[桥](https://ethereum.org/developers/docs/bridges/)、[IBC](https://ibcprotocol.dev/about)。具体新模式见 [多链升级教程](upgrades/03-multichain.md)。

## 19. 不动真钱，也能学会读一笔交易

**区块浏览器 explorer**把链上数据组织成人能读的页面；它是观察工具，不是协议本身，也不是页面显示什么就独立验证了什么。地址标签、价格、代币图标和源码匹配等往往来自额外索引。

本次没有实际访问你的地址或执行以下实验。学习时可选公开交易或离线示例，先不连接钱包、不输入恢复材料。

先标网络：主网有真实经济价值；**测试网**供测试使用；**本地开发链**可由你控制实验条件。长得相似的地址或相同 chainId 字段名称，不证明网络就是同一个。测试币也不能当主网币。

阅读一笔 BTC 付款，至少标出：

1. 交易标识 txid。
2. 每个输入引用哪个旧输出。
3. 哪个输出是目标收款，哪个可能是找零。
4. 输入总额、输出总额和差额手续费。
5. 所在区块及 blockHash、当前确认状态。

“可能是找零”是刻意保留的限制：浏览器启发式不能保证识别出真实收款人或经济目的。

阅读一笔 EVM 代币付款，至少标出：

1. 网络和交易标识。
2. 外层发送账户、nonce、目标合约及调用函数。
3. 实际 gasUsed、有效价格、执行状态。
4. 代币合约身份、数量的最小单位和 decimals。
5. 目标收款事件及实际资产变化。
6. 区块/最终性和平台自己的入账条件。

`receipt.status = 1`只是外层执行没有整体回退，不能无条件当作“预期数量已到指定收款人”。转账收费代币、可返回 false 的实现、聚合执行里的子调用失败，可能需要额外核对。

依据：[Bitcoin 交易参考](https://developer.bitcoin.org/reference/transactions.html)、[Ethereum JSON-RPC](https://ethereum.org/developers/docs/apis/json-rpc/)、[ERC-20](https://eips.ethereum.org/EIPS/eip-20)。上述字段检查是学习及工程核对框架，不是凭网页展示完成独立共识验证。

## 20. 安全扫盲：最危险的往往不是不会算哈希

公开链通常是**假名系统**，不是天然匿名系统。地址不直接写身份证，仍可能通过交易关系、平台身份记录等关联到人。公开数据不会因为你删除 App 就从历史消失。

对初学者，先认识这些不同层次的风险：

| 风险层 | 典型问题 | 不能混用的“解决方案” |
| --- | --- | --- |
| 控制材料 | 私钥/助记词泄露、备份丢失 | 链没有出故障，不代表密钥安全 |
| 授权与界面 | 恶意签名、无限额度、假网站、地址替换 | 硬件签名不代表业务意图正确 |
| 程序与权限 | 漏洞、代理升级、管理员滥用、预言机异常 | 审计报告不等于无漏洞保证 |
| 网络与跨链 | 重组、排序器停机、桥验证失败、数据不可用 | 源链正常不证明目标链资产可退出 |
| 托管与兑付 | 平台资金缺口、储备风险、冻结、退出限制 | 链上能查余额不证明所有负债被覆盖 |
| 经济与法律 | 流动性消失、清算、脱锚、业务资格变化 | 技术可调用不等于收益确定或依法可用 |

把下面几条当作学习阶段的最低约束：

- 不把助记词/私钥输入网页、聊天、工单或这个仓库；“客服需要帮你恢复”不是例外。
- 不能理解签名内容、授权对象或网络时先停，不把“免费签一下”当安全保证。
- 从可信来源核对网络、合约和目标地址，不只看币名、图标或地址首尾几个字符。
- 断开网站连接、撤销 allowance、撤销 7702 委托是不同操作，不把它们当同一个按钮。
- 不把陌生到账资产或空投当邀请，更不因看到代币而去它给的网站“解锁”。
- 升级协议通常不需要把原生币转给所谓升级客服；钱包界面更新也不需要交出恢复材料。
- 大额操作前应另行设计完整授权、备份恢复、故障和对账验证；本文不授权任何资金操作。

## 21. 给整个行业一张地图：不要把它只理解为炒币

读到这里，可以按职责而非币名认识行业：

```text
基础协议：共识、执行、数据与结算
  ├─ 基础设施：节点/RPC、索引、预言机、开发工具
  ├─ 控制与账户：钱包、多签、MPC、托管、智能账户
  ├─ 资产与连接：原生币、代币、稳定币、跨链/桥
  └─ 应用：交易、借贷、支付、基金份额、游戏/身份等

每层都还依赖：治理、运营、安全，以及相应法律与商业关系
```

**支付**关注资金如何转移及最终收款；**交易**关注资产交换和定价；**借贷**关注债务与抵押；**RWA，现实资产代币化**关注链上记录代表哪种链外权利。相似的转账操作，可以对应很不同的商业活动。

例如代币化国债基金份额，可能代表基金权益，不表示你直接拥有基金中的某一张国债，也不自动成为支付稳定币。资产管理人、托管人、转让代理、资格和赎回流程仍有作用。

目前哪些已上线、哪些仍在规划、哪些旧服务已退役，放在单独的 [2026-10-29 行业现状](industry-status-2026-10-29.md)。这样基础知识不会因为一次升级而整体过期，时间敏感结论也有明确核验日期。

看一个项目时，用这七问代替口号：

1. 它解决谁的什么问题，为什么不用现有数据库或支付接口？
2. 链上记录的究竟是原生资产、合约数量，还是链外请求权？
3. 谁能授权、冻结、升级或更改参数？
4. 交易执行、共识稳定和业务结算各靠什么证据？
5. 数据从哪来，数据源或服务离线后怎么办？
6. 资产从哪进入、怎样退出，正常路径失败时还有没有可用出口？
7. 产品、用户、收入和代币价格之间有哪些真正可核验的联系？

这七问是本教程的分析框架；具名产品证据见 [稳定币、支付与 RWA 来源审计](notes/beginner-industry-source-audit.md)。它不推定所有产品都适合所有地区用户。

## 22. 自测与练习：能讲清楚，才算完成扫盲

先不看答案，试着每题用两三句话解释。不要求写密码学公式。

| 自测问题 | 答案要点 |
| --- | --- |
| 复制钱包文件为什么不会复制出更多 BTC？ | 文件可能复制控制材料，金额仍来自同一账本；同一输出不能在同一有效历史中花两次。 |
| 哈希、加密、签名是不是一回事？ | 哈希做摘要，加密保护内容，签名证明相应授权及消息完整性。 |
| 没有矿工，普通全节点是不是没用了？ | 独立验证仍是重要角色；验证规则与竞争出块权分开。 |
| 候选区块里的交易合法，为什么还要不停算？ | 内容有效和 PoW 达标是两项检查，合法内容不保证头哈希足够小。 |
| 小目标让挖矿更容易还是更难？ | 更难；允许结果的范围更小。 |
| 谁把难度结果发给全网？ | 不存在中央发放者；节点按规则和历史独立计算，并检查矿工声明的 nBits。 |
| 算力翻倍，长期平均一定每五分钟出块吗？ | 短期可能更快，周期调整会提高难度；目标平均间隔仍约十分钟。 |
| 矿工奖励里的手续费是新发行吗？ | 不是，补贴是新增，手续费来自既有资产。 |
| 0.10 BTC 的输入支付 0.03 BTC，剩下的在哪？ | 通常用新找零输出返还，扣除费用；旧输入完整被消耗。 |
| 签名合法能否证明不存在双花？ | 不能；两笔冲突交易都可能签名合法，排序与当前状态限制最终花费。 |
| RPC 返回交易标识，意味着收款人拿到钱吗？ | 不意味着；还需核对包含、执行效果、稳定性和业务入账。 |
| 转 ERC-20 时最外层 to 为什么可能不是小周？ | 它是被调用的代币合约，小周在调用参数及相应资产变更中。 |
| 合约回退为什么仍可能支付费用？ | 已执行消耗资源；普通业务状态回滚不等于费用和发送方 nonce 回滚。 |
| Disconnect 为什么不等于 revoke？ | 断开网页会话，不自动撤销链上额度或委托。 |
| “有审计”“ZK”“自托管”是否分别等于安全、隐私、无依赖？ | 都不等于；需要查报告范围、证明对象与其他服务/权限边界。 |
| 稳定币能转账，是否保证任何人直接拿回美元？ | 不保证；发行方支持、资格、兑付条款与银行结算是独立边界。 |
| 100 shares 为什么不一定等于 100 assets？ | shares 是份额，换算率和退出条件取决于金库机制及状态。 |
| IBC 或桥连接两个网络，是不是共用安全？ | 不自动共用；通信、共识、数据和托管有各自机制。 |
| 一枚 NFT 为什么不自动等于版权？ | 编号及转移标准本身不规定全部链外法律权利。 |
| 为什么不能用币价上涨证明协议安全？ | 价格与规则、实现、控制权和可验证证据是不同问题。 |

### 四个零资金练习

1. **转账拆解**：用第 7 节数字复述 BTC 付款。自己改成两个输入，保持输入 = 输出 + 费用。
2. **难度方向**：画出目标为 `0009`和`0019`时的合格范围，解释哪个更容易。不要把教学编号当真实哈希。
3. **产品风险卡**：选一个公开产品，只填“资产身份、控制者、收益来源、数据源、退出方式、未核验事项”，找不到证据就写未知。
4. **失败状态卡**：分别解释广播超时、执行回退、重组、稳定币脱锚、桥停机；每个写需要补查什么，避免都称为“转账失败”。

愿意读少量代码时，运行已有 [离线练习程序](examples/offline_workbook.py)：

```bash
python wiki/topics/blockchain/examples/offline_workbook.py
```

该程序演示难度方向、费用、精度、预留、幂等与重组，不生成生产密钥、不联网、不广播。通过教学测试不证明真实钱包安全。

### 扫盲之后怎么继续

- 想先理解产品和行业：读 [行业现状](industry-status-2026-10-29.md)，练习区分事实、公告和推论。
- 想理解协议内部：读 [Bitcoin](chapters/02-bitcoin.md)、[Ethereum](chapters/03-ethereum.md) 和 [术语表](glossary.md)。
- 想做钱包工程：读 [钱包工程](chapters/05-wallet-engineering.md)、[安全](chapters/06-security.md)，按 [学习路线](learning-roadmap.md)验收。
- 想看旧知识升级后怎样变化：进入 [升级教程](upgrades/README.md)，不要把旧参数、提案与现行网络混用。

最后应记住的不是币名，而是一条检查顺序：**资产是什么 → 谁能控制 → 交易如何执行 → 历史怎样稳定 → 数据如何核对 → 价值怎样兑现和退出。**
