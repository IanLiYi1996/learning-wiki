## 1. 编辑结论：把“可验证”后面的宾语补全

建议全书反复追问：**它验证的是名称配置、某次签名、文件字节、存储承诺、设备服务，还是现实身份与商业需求？** 这些不是同一命题。下面的类比均为本文教学设计，不是官方担保。

| 应用对象 | 好懂的入口 | 必须立即补上的边界 | 依据 |
| --- | --- | --- | --- |
| ENS／身份 | 电话簿、门牌与开门钥匙 | 查到地址、能签名，不等于知道现实中的人是谁 | S01–S03 |
| IPFS | 按内容指纹找书 | 指纹能校验内容，不能让没有副本的书重新出现 | S04、S05 |
| Filecoin | 有期限的仓储约定加巡检 | 验证存储承诺，不验证书里叙述的真实性 | S05、S06 |
| DePIN | 用奖励协调人们提供基础设施 | 奖励或合资格流量，不直接证明无补贴需求及盈利 | S07；分析见第 4 节 |
| 预言机 | 把外部读数交给程序的报数员 | 验证报数来源／传输，不自动验证现实事实 | S08 |

| 多链身份 | 地址前先写清城市 | 标识用于区分网络，不是证明端点诚实的密码 | S10 |

## 2. ENS 与去中心化身份：名字指向谁，和谁能改名字，是两回事

### 2.1 ENS：电话簿不是户籍簿

ENS 的入门用途是将人可读名字解析为地址。应把三个问题分开：谁持有名字或相关配置权限、resolver 当前给出什么地址、该地址与什么现实主体有关。名称持有者与记录写入者的权限可能不同；S01 的子名称例子明确显示，持有子名称不自动具有父级 resolver 的写入权限。[S01]

教学例：小林持有 `xiaolin.eth`，却把收款记录设为另一个地址。查询名字只是得到当前指定的收款位置，不能由此推断该地址就是名字持有者，更不能推断它对应现实中的小林本人。这是由可配置记录机制推出的例子，不是对真实名称的查询结果。[S01]

反向解析也不能单独当身份证明：地址声明的名字必须再正向解析，并在相应链的地址记录语境下回到原地址；不匹配时显示原地址。不同链的记录可能不同。双向匹配证明的是名称—地址关系符合该检查，不是“认证为某品牌／自然人”。后一句是证据边界判断。[S02]

类比到此为止：电话簿说明“名字指向哪里”，不说明联系人是谁、是否可信。改稿不要将 ENS 一律写成永久所有权、所有子名权限相同，或让“解析成功”替代现实身份核验；注册与权限细节须按具体版本另查。

### 2.2 DID：标识、控制者、被描述对象要分开

DID 是一种标识符及相关文档机制，不是“全民身份证链”。W3C DID Core 区分 subject（被标识的对象）与 controller（能按该 method 的规则更改文档者）；两者可以不同。DID 也不要求全部使用区块链，具体创建、解析、更新、停用规则由 method 定义。[S03 §1.3、§8]

教学例：设备厂商管理一台传感器的 DID，厂商是控制者，设备是被描述对象。有效认证证明的是符合相应验证关系的控制／使用能力，不自动证明设备读数准确，或签名者的现实姓名。现实身份绑定还需要另外的可信声明与核验；凭证也须另审发行者及有效性。[S03 §5.3、§9.2；后两项为审查建议]

类比限制：“拿得出钥匙”不是“法律上就是房主”。ENS 的人可读名字与 DID 的标识体系也不是同一标准。不要把签名验真写成实名验真、把一个 DID 写成永远对应同一人；公开标识和文档还可能带来关联风险。[S03 §9.16、§10.2–10.3]

## 3. IPFS 与 Filecoin：校验内容、保留副本、履行存储约定分别看

### 3.1 IPFS：内容地址不是永久备份承诺

IPFS 的 CID 是内容标识，不是某台服务器的位置。它含有内容哈希及编码等信息；文件可能被分块并组织成 DAG，所以不能简单把 CID 等同于整个文件的 SHA-256。相同文件采用不同分块、编码等设置可以产生不同 CID。[S04]

教学例：图书的“内容指纹”能帮助检查取到的是不是此前选定的那份内容，但指纹不是图书本身。校验成功只说明数据与该标识匹配；假报告也能有合法 CID。谁发布了应该使用的 CID、报告是否属实，是另一个问题。[S04；后两句为逻辑推论]

IPFS 节点可以缓存数据，也可以垃圾回收；pinning 是让指定节点保留数据的机制，不是命令全网永久保存。若没有可提供内容的副本，仅有 CID 不足以取回文件。付费 pinning 还依赖服务持续运行及有人承担成本。[S05]

类比限制：不要写“上传一次，全球永存”“每个 IPFS 节点都存所有文件”，也不要把有 CID 当成所有权或隐私证明。改稿可用一句话收束：**内容寻址回答找哪份，持久化回答谁继续保存。**[S04、S05；收束句为教学设计]

### 3.2 Filecoin：有期限的存储承诺，不是通用真理证明

Filecoin 的存储 deal 是客户与存储提供者按数据量、期限、价格等达成的协议约定，不宜仅因中文用了“合约”便让读者以为每次都在部署 Solidity。PoRep 验证特定提供者创建了相应的编码副本，PoSt 用后续挑战验证持续存储；证明对象是约定数据的存储状态。[S05、S06]

教学例：仓库按约保存装有报告的箱子，并接受巡检。即使报告是伪造的，“保存了这些字节”和“报告内容属实”仍是不同命题。独特编码副本也不能直接推导为地理位置分散、运营主体彼此独立。[S06；真实性与独立性边界为推论]

存储证明不自动保证任何用户随时通过任意网关快速下载。检索是另一个服务过程，期限、续约、可用副本及实际取回测试仍需检查；本文未执行这些检查。IPFS 可以不使用 Filecoin，取得 CID 也不自动建立 Filecoin deal。[S05、S06]

类比限制：协议挑战不是人逐字逐秒看守文件；通过证明不是“永不丢失”、内容版权确认或现实事实背书。本书不展开其他存储证明路线，更不把一种路线概括为整个 Filecoin 产品栈。

## 4. DePIN：有奖励、有服务、有需求，是三层问题

本书可将 DePIN（去中心化物理基础设施网络）作为一种应用思路介绍：用网络与激励协调人们提供真实基础设施，而不是把它当成一种统一共识算法。代表性例子取 Helium 官方 Mobile 文档：社区运营热点或既有 Wi-Fi 网络提供无线服务，奖励按合资格数据传输计算，设备就绪程度与服务质量影响参与资格。[S07；分类口径为本文教学整理]

教学入口：“社区一起建设并运营通信设施，协议按规则计量和奖励。”但这只能引出机制，不能代替需求研究。

以下是由“合资格服务量”与“奖励规则”的区别推出的经济审查框架，不是 Helium 或整个 DePIN 行业的经营结论：

1. **供给**：设备数、覆盖范围或可用容量，回答提供了什么。
2. **使用**：计量到的服务量及排除作弊的规则，回答哪些使用被系统认可。
3. **需求**：谁为服务付钱、是否依赖补贴、是否持续购买，不能只由奖励数或设备数推出。
4. **可持续性**：客户付款、补贴／代币奖励与部署运维成本应分开看，不能把发出奖励直接写成营业收入或盈利。[S07；1–4 为分析建议]

类比限制：补贴建成停车位，不等于有人愿意持续付费停车；即便发生流量，也还需要辨认其来源与补贴条件。不要断言“所有 DePIN 都是真需求”，也不要反向断言“所有都是空转”。本次没有客户账单、收入／成本审计或独立流量样本，不填需求规模及收益数字。

不把历史 Proof-of-Coverage 奖励规则直接当作 2026 年所有 Helium 网络、或所有 DePIN 的现行规则；不同服务与时期须单独查证。本文只采用 S07 可读正文，不另做奖励升级时间线。

## 5. 预言机：链统一接受输入，不等于输入天然正确

Ethereum 合约默认不能直接访问链外资料。预言机把外部数据提供给链上程序，解决共同使用输入的问题，同时引入来源、正确性、更新与可用性的依赖。多个报数节点若依赖同一个上游，仍保留共同来源风险。[S08]

教学例：保险程序收到“降雨不足”的报告后按规则执行。链能让参与者核查使用了哪份输入、如何执行，却不能仅凭执行成功证明田地真的缺水。签名或传输完整性证明可以保护“谁报了这个数、途中是否被改”，不能把错误来源变成真实事实。[S08；田地例子为推论]

建议正文用四个问题替代“oracle 把真相上链”：来源测量什么；采用什么时间与单位；谁报送／聚合；过时、分歧或不可用时怎样处理。讨论价格时还要明确是哪种资产和市场口径。这是接口审查建议，不是声称本次验证了具体数据馈送。[S08]

类比限制：报数员不是全知裁判。多节点不必然是多独立来源；若链上自动执行使用了错误数据，自动化会忠实执行错误输入下的规则，而不是纠正现实。[S08]

## 6. 区块链与数据库：先问共享账本解决哪种不信任

“数据库存数据，区块链保证真实”应删除。Fabric 官方说明同时涉及数据库、交易排序、成员身份和应用背书策略：链与数据库不是互斥产品；共同验证交易也不能自动解决链外录入事实是否正确的问题。[S09；事实边界为推论]

教学入口：供应商、仓库、采购方各保留按共同规则形成的业务记录，减少完全依赖某一方单独维护记录的需要。类比限制：大家保留一致的“已签收”记录，不等于证明货物没有损坏；错误还需要业务更正与争议处理。

下面是选型建议，不是本次跑出的数据库性能对比：

- 若所有参与者愿意接受一个可信运营者，先评估普通数据库、权限控制与审计日志是否足够，不为“上链”本身增加网络。
- 若需要多组织共同确认状态，先写清谁有权提交、背书、排序、更改规则与处理争议；不能只画“多个节点”。
- 核算复制数据、验证、共识与运维的成本，并将延迟、吞吐、查询、隐私及更正／删除需求分别列为验收条件；不宣称区块链必然更快、更便宜或更省存储。
- 大文件与敏感资料的保存需求，不能只凭链上放一个哈希解决；完整性、持久化和访问控制仍需另行设计。[S09；存储边界另据 S04、S05]

许可网络也不是“假区块链”。Fabric 通过已识别参与者及治理规则运行，不要求原生加密货币支付挖矿激励；channel 和 private data 提供限制数据分发的能力。其可信性与保密性仍取决于成员、策略和配置，不由“联盟链”三个字自动获得。[S09]

不要把 public／permissioned 简化为“有没有币”，也不要把无原生币写成无成本、无管理员风险。本文使用 Fabric 2.5 文档说明机制，不据其介绍页给当前市场排名或新版本部署建议。

## 7. 多链与互操作：在地址之前先写网络身份

### 7.1 可读的名字不是已验证的网络

CAIP-2 使用 `namespace:reference` 区分不同体系的链，例如 `eip155:1` 是规范中的 Ethereum 主网示例。EVM 的数字 chain ID 不能单独表达所有 Bitcoin、Cosmos 等网络；各 namespace 的解析语义另有定义。[S10]

教学例：两个城市都有“中山路 8 号”。只给门牌不够，应连同城市一起辨认。类似地，审核资产与收款目标至少写清网络、账户／地址，以及适用的合约、mint 或其他资产标识，而不是只写币名。Solana mint 作为资产标识的例子见 S11。[S10、S11；最小审核记录为建议]

类比限制：写了城市名不证明司机开到了那里。CAIP-2 定义标识格式，不认证 RPC 服务端、不验证共识或背书资产；所以不能只因端点自报一个正确 chain ID，就认为连接已可信。这是从规范作用域得出的安全推论，不是本次发现了某个恶意端点。[S10]

### 7.2 “能连接”与“能兑现”分开审查

建议主线程将互操作拆成以下审查问题，而非一个“全链打通”图标：

1. 对象是否指向正确网络、账户与资产？
2. 消息由谁传递，接收方按什么证据接受源状态？
3. 到达后由哪个程序执行，失败或超时由谁处理？
4. 若涉及资产表示，谁承担保管、发行或兑付责任？

这是编辑与安全检查框架，不是 CAIP-2 提供上述四项保证。**标准化标识不等于跨链验证，消息送达不等于业务完成，业务完成也不自动等于有可兑现的同一资产。**[S10 仅支持标识层；其余为必须另取证的检查项目]

关于 IBC／XCM、共享安全和桥资产会计，既有[生态审计](ecosystem-source-audit.md)与[多链升级教程](../upgrades/03-multichain.md)已有专项材料，本任务不复制其机制与升级状态。

## 8. 非 EVM 代表类别：只补初学者缺少的分类锚点

现有入门稿以 Bitcoin 与 Ethereum 为主。下列只建议插入短说明，避免读者把一种资产模型或一种 L2 形态套到所有网络；不是再写一轮旧笔记或最新升级审计。

- **Solana：补“资产怎么表示”的一段。** Token Program 提供操作逻辑，Mint 标识一种资产，Token Account 记录相应余额与权限；ATA 是特定可推导地址的 Token Account。不要把所有代币都画成各自独立部署的 ERC-20 合约。类比可用“公共操作程序、商品编号、个人库存记录”，但这不是数据库表的逐项对应。[S11]
- **Bitcoin／Lightning：补“同一资产的不同付款路径”的一段。** BOLT 将 Lightning 定义为基于通道的链下 Bitcoin 转移协议，必要时依赖链上交易执行约束；它不是另一种必需的独立代币，也不应仅凭同叫 L2 就套用 rollup 流程。类比可用“先约束资金，再更新双方认可的付款状态”，不能说成“随便记账、最后链自动兜底”。[S12；分类区别为教学推论]
- **Cosmos SDK／IBC、Polkadot coretime：不新增展开。** 本次没有发现超出既有专项材料、需要再做机制审计的新缺口；由主线程选择如何压缩成入门分类卡，不重复工程、迁移及部署细节。

S11、S12 只服务于上述分类锚点；详细权限、扩展、通道处置和安全条件仍回到原专题。本文没有执行 token 或 Lightning 实验。

4. **滚动文档不是历史归档。** 除固定 DID 规范与 BOLT 提交外，多数 URL 可以变化；本文未保存网页归档。2026-10-29 的核验记录不能重建该日每一时刻的部署状态，更不能推断日后状态。
