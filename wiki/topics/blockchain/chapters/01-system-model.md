# 01｜系统模型与信任边界

- 对应 PPT：3–7、23–25、60
- 学习目标：区分“签名合法”“交易有效”“被打包”“可入账”
- 来源：[来源表](../sources.md)中的 B01、B02、E01、E02、E03

## 1. 区块链维护的对象

可以先把区块链理解成一套复制状态机：各节点按协议检查交易，以共识决定的区块顺序执行，获得下一份状态。这是学习抽象，不代表 Bitcoin 和 Ethereum 使用相同数据库。

```text
Bitcoin：当前未花费输出集合 UTXO
         + 按脚本验证的花费规则

Ethereum：账户状态 + 合约存储
          + 按 EVM 规则执行的状态转换
```

Bitcoin 的交易消耗已有输出、创建新输出；Ethereum 的交易改变余额、nonce、存储等状态。签名只是授权输入，不能独自决定顺序或证明余额足够。[B01][E01][E02]

## 2. 把 PPT 的“四重防线”拆成职责

| 机制 | 验证的问题 | 无法独自保证的事 |
| --- | --- | --- |
| 数字签名 / 脚本 | 此交易满足花费授权吗 | 两笔合法冲突交易哪笔最终生效 |
| 状态检查 | 输入存在且未花费吗；nonce 和余额满足规则吗 | 全网最终选择哪条历史 |
| 共识与分叉选择 | 对有效候选历史如何排序与选择 | 无效签名变合法；链外资产一定存在 |
| 确认 / finality 策略 | 何时把观察转为业务承诺 | 所有层面的风险都降为零 |

Bitcoin 节点先验证协议规则，再在有效链之间比较累计工作量。多数算力也不能让全节点接受伪造签名或违规增发。经典攻击模型里，确认降低少数算力攻击者追赶的概率，但不是无限条件下的数学担保。[B01][B02]

## 3. 五种容易混淆的“信任”

以下是本次工程分析框架：

1. **协议信任**：哈希、签名、共识和客户端实现是否正确。
2. **观测信任**：RPC 有没有落后、漏日志、返回错误网络的数据。
3. **控制信任**：私钥、签名服务、升级管理员、模块由谁控制。
4. **资产信任**：USDT 储备、桥托管、USDe 对冲头寸是否能兑现。
5. **业务信任**：内部账本有没有重复入账、错误回调、未批准提现。

全节点主要减少对远程节点的依赖，不能代替后四项治理。Merkle proof 能证明某值属于可信根承诺的状态，不能证明发行方的银行余额。[E03]

<!-- /illustration: transaction-trust-boundaries-40d181a126 -->

```text
用户意图
  → 业务审批（允许做什么）
  → 交易构造（究竟会做什么）
  → 签名策略（独立核对两者）
  → 链上广播与执行（是否真的发生）
  → 观察与账务（如何承认、撤回和对账）
```

这是设计建议。生产系统应让审批绑定交易的具体语义，而不是仅绑定“调用一次 KMS”或某个不可读的哈希。因为上链有效不等于符合企业意图，密钥不导出也不等于签名服务不会签错交易。

## 5. 对比时使用同一坐标系

不要用“Ethereum 安全、Solana 快”结束讨论。先固定：

- 交易类型和资产类型；
- 包含、确认、最终性各自的延迟；
- 是否把投票交易算作 TPS；
- 负载下的费用和失败率；
- 验证者与只读节点的硬件区别；
- 升级控制、节点多样性、数据可用性和退出路径。

这是比较方法，不是本次性能测量。本专题不沿用 PPT 的 TPS、币价和市场份额作为当前指标。

## 自测

“交易签名合法、RPC 返回交易哈希，但用户还没收到资产”是否矛盾？

不矛盾。签名、广播接收、区块包含、执行结果、资产到账和业务入账是不同阶段。沿边界逐项检查，比反复重发一笔新交易更有价值。
