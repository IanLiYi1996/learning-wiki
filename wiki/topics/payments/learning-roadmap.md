## 实验 A：模拟“一次成功但响应丢了”

不接真实支付 API，不使用真实账号或卡号。

设商户支付意图为 `order-001-attempt-1`：

1. 第一次请求发出，通道已经处理，商户没有收到响应。
2. 用同一个业务意图和幂等键重试。
3. 服务方把最终结果以两个相同事件发来。
4. 又来一个较旧状态的事件。
5. 订单履约和账务效果最终只发生一次，旧状态不能覆盖新状态。

写出你会保留的 5 个标识：订单 ID、支付意图／尝试 ID、通道交易 ID、事件 ID、账务事件 ID。

**通过条件**：能解释每个标识负责哪种防重，而不是只说“加一个 UUID”。具体实现仍要遵守选用服务方的规则。[IDEMPOTENCY](sources.md#idempotency) [WEBHOOKS](sources.md#webhooks)

## 实验 B：100 元模拟 PSP 账本

沿用读本第 09 课的简化模式，金额均为教学假设：

- 收款 100.00。
- 商户应付 97.50。
- 伙伴费用应付 1.90。
- 本例服务部分 0.60。

记下收款、商户出款、伙伴费用支付三组分录，检查每组借贷平衡。之后问：

1. 收款刚进银行时，为什么不能说公司赚了 100？
2. 商户出款后，账上剩余的 2.50 为什么也不全属于 PSP？
3. 如果第二次出款请求超时，重复记账会使哪个约束破坏？
4. 若退款只记在订单系统，银行流水发生变化后，对账会看到什么？

**通过条件**：不用真实资金，能把银行资产、商户债务、伙伴债务和示例收入分开；理解生产会计还需增加其他账户、调整与确认规则。

## 实验 C：一页产品研究

选一个你熟悉的支付产品，使用它自己的产品说明、合同／法律页面和固定报告期披露。不要先看二手榜单。

填九格：

| 格 | 你需要找的事实 |
| --- | --- |
| 客户 | 商户、消费者、平台还是企业 |
| 场景 | 购买、汇款、供应商付款、出款还是发卡 |
| 凭证与资金 | 余额、卡、账户还是链上资产 |
| Rail | 使用哪个网络，有哪些伙伴 |
| 主体与责任 | 哪个法人，谁管客户资金、授权与损失 |
| 收入 | 收什么费，如何列报 |
| 指标 | 固定报告期、币种、分子分母 |
| 风险 | 欺诈、信用、资金、监管与运营 |
| 技术假设 | 有什么问题，预算／负责人／架构／ROI 证据是什么 |

**通过条件**：把“事实”“计算”“推论”“不知道”分开；不拿技术假设当已经部署的证据。

## 11 个课后问题参考答案

答案为读本内容的简短复盘，不增加新事实；机制来源跟随对应课程。

1. **二维码为什么可以走不同 Rail？** 它是入口／信息承载形式，不直接定义钱怎样结算。
2. **授权后商户是否已有现金？** 没有这个保证，需继续观察请款、结算与出款安排。
3. **接入插件会自然成为 PayFac／MoR 吗？** 不会。网络、合同与交易责任要单独辨认。
4. **为什么先看 Take Rate 口径？** 不同收入与支付量范围相除，比较会误导。
5. **虚拟卡、Token、储值钱包改变什么？** 分别偏向卡产品形态、凭证表达、余额／资金模式。
6. **实时为什么不等于卡式拒付？** 速度与争议制度是不同维度。
7. **本地跨境出款为什么仍看流动性？** 目的地可用资金和后续再平衡仍需安排。
8. **KYC、3DS、PCI、资金保护为什么不能互替？** 它们回答不同问题。
9. **一次 Webhook 为什么不能证明账正确？** 仍可能缺事件、重复副作用或记录与实际资金不符。
10. **利润率下降说明要上云吗？** 不说明。需先找成本／组合／风险原因，再验证项目。
11. **代理金额和用途控制在哪里执行？** 在可信授权与支付执行控制中，不能仅靠模型“记住”。

## 进阶自测：十句判断题

先遮住答案，逐句判断。正确答案是所有说法都不成立：

| 说法 | 错在什么地方 |
| --- | --- |
| 一个品牌只属于支付行业一类 | 角色、产品、场景可组合 |
| 实时支付就是 RTGS | 即时客户可用性不确定银行间结算模式 |
| 跨境一定发生换汇 | 同币种也可跨境 |
| SWIFT 发送成功就是客户到账 | 报文与资金／账户记入不同 |
| 客户余额就是公司的收入 | 客户权益与公司经济价值不同 |
| 交易量涨 50%，收入必然涨 50% | 收入率和组合可以改变 |
| 3DS 通过就不会拒付 | 认证与全部争议风险不同 |
| 用 Token 就没有 PCI 责任 | 范围取决于具体 Token 与实际环境 |
| 消息只到一次所以不用幂等 | 其他重试、并发与恢复仍可能重复副作用 |
| AI 自动下单意味着可以无限付款 | 用户委托必须有可信、有限的执行边界 |

## 下一层读什么

- 做产品／行业讨论：网络规则、角色合同、具体市场的监管页面。
- 做研发：提供方状态／错误语义、幂等、异步事件、账务与对账资料。
- 做跨境：CPMI 代理行与 PvP，目的地支付网络、资金保护及伙伴安排。
- 做销售／解决方案：先拿到真实失败原因、处理成本与运营痛点，再讨论 Workload。

本专题是起点，不是把监管、会计、网络认证与生产工程一次性学完的替代品。
