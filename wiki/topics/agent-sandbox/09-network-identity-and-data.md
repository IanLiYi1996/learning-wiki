# 09｜网络、身份与数据：把执行隔离接到授权边界

研究日期：2026-11-04。

本章关注 agent sandbox / microVM 部署中的网络出口、业务身份与数据流转。资料核验仅包含官方文档和第一方代码的在线阅读；未部署环境、运行安全测试或验证任何供应商的安全保证。文中“官方机制”表示来源描述，“教学建议”表示本章提出的部署设计与验收要求，两者不能混同。

## 1. 先分清：沙箱边界不是业务授权边界

OWASP 将外部网页、文件等内容影响模型行为归为间接提示注入，并建议通过最小权限、代码处理敏感功能和高风险操作的人类审批限制影响。因此，本章的架构推论是：即使执行环境没有逃逸，agent 仍可能在已获准的 API 或浏览器会话中做出不符合用户意图的操作；VM 不能替代业务授权，也不能证明提示注入已被消除。[来源：OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)

教学建议：威胁建模至少拆成四个问题，并分别指定执行检查的组件。

| 边界 | 要回答的问题 | 教学建议：检查位置 |
| --- | --- | --- |
| 工作负载边界 | 代码能读哪些文件、创建哪些进程、消耗多少资源？ | guest / 容器内限制，加宿主运行时与资源配额 |
| 控制面边界 | 谁能创建、连接、改变策略、附加身份或销毁实例？ | gateway 的身份认证、租户授权与管理审计 |
| 凭证与业务边界 | 当前任务能以谁的身份，对哪个资源执行什么动作？ | sandbox 外的 broker、工具网关及业务服务端 |
| 输出与数据边界 | 哪些文件、日志、模型输入和结果可以离开任务？ | 出口代理、导出服务、日志管道及人工交付环节 |

教学建议：不要用“都在同一台 VM 里”回答上述四个问题。将代码、下载的依赖、网页、仓库文件、MCP 返回内容和模型生成的参数视为不可信输入；将批准者、策略服务和凭证签发者置于工作负载不可修改的位置。

## 2. 教学参考架构：每条能力都有独立入口

下面是教学建议，不是 OpenShell 的部署图，也不是已经验证的实现。代理、broker 和导出服务的可信代码仍需独立保护。

```text
用户 / 审批者
      |
      v
控制面：认证、租户检查、任务与策略版本
      |                         |
      | 创建 / 撤销             | 授权记录
      v                         v
+------------------+    凭证 broker / 受控工具网关 ---> 指定业务 API
| 不可信工作负载    |           ^    逐次检查任务、资源与动作
| agent + 执行环境  |-----------|
| 文件 / 浏览器     |
+------------------+
      | 网络请求                 | 产物 / 日志
      v                          v
出口代理 + 受控 DNS            导出校验 / 日志脱敏
      |                          |
      v                          v
批准的模型、仓库、服务          当前租户的交付与审计存储
```

教学建议：将一次权限授予记录为 `租户 + 用户 + task_id + sandbox_id + 实例代次 + 动作 + 资源 + 有效期 + 策略版本`。请求中的这些字段不能由 agent 自报后直接采信，应与控制面的可信记录关联。

教学建议：授权不仅发生在创建时。任务取消、用户撤销、角色变化、实例重建或策略收紧时，broker、工具网关、连接会话和导出服务都应重新检查；无法确定状态时拒绝新操作，而不是沿用缓存中的宽权限。

## 3. 网络出口：默认拒绝之后，还要验证什么

### 3.1 Kubernetes NetworkPolicy 的能力边界

Kubernetes 官方将 NetworkPolicy 定位在 IP、端口与 L3/L4 流量控制，实际执行需要支持它的网络插件。策略的允许规则是叠加的：增加一个允许全部出口的策略，不能再靠另一个 NetworkPolicy 把出口收回。它不提供 TLS 控制、强制公共网关路径或标准化的网络安全事件日志。[来源：Kubernetes Network Policies](https://kubernetes.io/docs/concepts/services-networking/network-policies/)

同一官方文档还指出：`hostNetwork` 行为依赖实现，所在节点的流量存在例外；策略变更对已有连接的影响由实现决定。默认拒绝出口也会阻断 DNS，需要按需添加解析服务的允许规则。[来源：Kubernetes Network Policies](https://kubernetes.io/docs/concepts/services-networking/network-policies/)

教学建议：不要把“YAML 已提交”“Pod 已启动”或“有 egress policy”当作有效阻断证据。对 Kubernetes、容器和 microVM，都应明确真正执行出口限制的位置，以及 guest、宿主转发、sidecar、代理和控制面各自有哪些例外。网络插件能力不能由对象名称推断。

### 3.2 教学建议：完整的出口检查链

本节全部是设计要求与待验收项目，不表示 OpenShell 或其他产品已实现、已测试以下每一项。

1. **先建立不可绕过的路径。** 工作负载只能访问批准的中介入口；不能仅依靠 `HTTP_PROXY` 等环境变量。分别约束直接 TCP、UDP、IPv4、IPv6、额外网卡与宿主转发路径。代理失联、策略不可用时，不允许回退直连。
2. **解析也经过受控边界。** 只开放指定 DNS 服务；明确处理 TCP/UDP DNS、客户端自选解析器以及经 HTTPS/TLS 发送的解析请求。允许解析服务不等于允许任意查询内容，对查询量、名称长度与必要域名范围另设约束。
3. **域名批准和实际地址批准分开。** 规范化目标域名、端口与 URL；由可信组件处理 A、AAAA、别名链及缓存。对所有候选地址执行地址分类，连接只能使用已检查的地址，不能检查一次后让另一个组件独立重新解析。
4. **把 DNS rebinding 当作检查时序问题。** 每次新连接、重新解析、TTL 更新与连接池重建都重新判断目标。既检查名称，也检查最终连接地址，避免“初次解析可接受，随后地址变化仍沿用授权”。
5. **内部地址默认禁止，例外必须具体。** 拒绝 loopback、链路本地、未指定地址、私有网段、节点及控制面地址、云元数据目的地。内部业务服务应通过显式服务身份、精确目标与窄范围地址约束放行，不能用“内网可信”作为总例外。
6. **IPv4 与 IPv6 同时验收。** 同时覆盖 IPv6 唯一本地地址、链路本地地址、IPv4 映射 IPv6 表示以及环境使用的地址转换路径。地址清单需由受维护的分类逻辑产生，不能把一份 IPv4 黑名单当作完整防线。
7. **重定向必须重新授权。** 默认不跟随未知目标；对每一跳重新检查协议、主机、端口、解析地址及授权。限制跳数；跨源请求不得自动带出原请求的凭证、Cookie 或敏感头，不能只审查最初的 URL。
8. **TLS 与代理职责写清楚。** 检查上游证书与主机名，明确谁终止 TLS、谁能看见请求内容、谁保管代理 CA 私钥。透传加密流量与解密后检查不是同等能力；必须检查的方法、路径、请求体或凭证绑定，不能留在不可见的通道里。
9. **获准出口仍要限制数据和动作。** 对模型、对象存储、工单、代码仓库等分别定义可发送的数据、方法、路径、资源及大小。批准访问一个域名，不代表批准向该域名上传整个工作区。

### 3.3 云元数据：阻断双栈地址，不依赖单一开关

AWS EC2 的 IMDS 地址包括 IPv4 `169.254.169.254` 和显式启用后的 IPv6 `[fd00:ec2::254]`；启用 IPv6 不会关闭 IPv4。IMDSv2 要求 token，而元数据响应 hop limit 是独立配置，AWS 提醒值为 1 在容器环境中可能引起问题。[来源：AWS IMDS options](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-options.html)

教学建议：不需要元数据的工作负载默认不能访问上述两个端点，也不能通过代理、宿主服务或重定向间接访问。宿主确有需求时，将宿主访问与 guest 访问分离，并检查实际实例配置；不要把 IMDSv2 或 hop limit 当成任务级授权。其他云平台需补充其官方端点与身份协议，不应直接套用 AWS 地址。

## 4. 凭证：把“拿到秘密”改成“获准使用能力”

OWASP 建议由应用代码处理敏感功能、不给模型不必要的权限，并对高风险动作引入人工审批。这提供的是分层防护原则，不是一套现成的凭证 broker 实现。[来源：OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)

### 4.1 教学建议：镜像、快照和 warm pool 不携带业务秘密

基础镜像与可复用快照只包含运行依赖和无身份状态。禁止烘入云访问密钥、个人 SSH key、生产 API token、浏览器登录资料、broker 刷新凭证及控制面签名密钥。快照模板也不应保存某个任务的授权句柄或登录后的进程状态。

教学建议：初始化时先完成租户与实例身份核验，再为当前任务分配能力。对恢复出来的实例重新生成身份、有效期和策略关联；不要因为磁盘或内存状态来自同一模板，就继承原任务的业务权限。warm pool 的复用应以状态清理与重新绑定成功为前提。

### 4.2 教学建议：broker 的最小接口

推荐优先使用“broker 在外部代为调用或签名”，而非把真实凭证交给 agent：

1. 控制面把经过批准的任务范围登记到 broker，包含资源、动作、租户、额度及期限。
2. 工作负载提出结构化请求；broker 验证可信的实例身份及当前任务状态，不采信模型生成的“已批准”文字。
3. broker 在允许的目标上使用受限凭证，返回业务结果或不透明能力句柄，不返回长期秘密。
4. 无法代理、确需向 guest 发放凭证时，签发短生命周期、明确受众与资源范围的凭证；避免个人账户与跨任务共享身份。
5. 任务结束或撤销后停止续期、撤销句柄并处理已有会话；上游不支持即时撤销时，记录剩余有效窗口。

教学建议：短生命周期只能缩短暴露窗口，不能替代范围约束；端点绑定只能限制秘密在哪里使用，不能自动判定该端点内的业务动作是否获准。broker 的刷新权限、密钥存储、管理员权限及审计能力也必须独立保护。

### 4.3 教学建议：特权 API 必须批准到具体任务

将部署、删除资源、向外发送消息、合并代码、变更访问控制等操作放在受控工具网关。先给用户展示规范化的动作、目标、关键参数与预计影响，批准后绑定请求摘要、当前任务、有效期和必要的使用次数。

执行时校验当前参数仍与批准内容一致，并在业务服务端再次做权限判断；不能把“用户允许使用某个工具”扩展成“任意参数都允许”。需要重试时，使用明确的幂等键与重试规则，防止一次批准产生多次副作用。

### 4.4 教学建议：grant / deny 示例

下表是教学授权模型，不是可直接复制的产品策略，也不是测试结果。

| 能力 | 可授予的最小范围（grant） | 默认拒绝（deny） |
| --- | --- | --- |
| 模型调用 | 本任务附加的 provider、允许的数据类别、额度和期限 | 任意模型服务、跨任务 provider、全量工作区上传 |
| 代码仓库 | 指定租户和仓库的只读查询；写入另行批准 | 组织级管理、未批准合并、跨仓库写入 |
| 对象存储 | 本任务输出前缀与大小上限 | 跨租户读取、桶管理、整个存储账户凭证 |
| 内部业务 API | 精确服务、方法、资源与审批后的参数 | 整段私网开放、仅凭 HTTP 方法推定安全 |
| 已登录浏览器 | 当前用户、指定站点、当前任务需要的页面动作 | 共用个人 profile、未知提交、跨租户会话 |
| 产物导出 | 导出清单中的文件，交付给指定租户接收者 | 任意宿主路径、自动执行、未经校验的归档内容 |
| 平台管理 | 仅控制面授权的管理员操作 | agent 自行改策略、附加高权限 provider、管理其他实例 |

## 5. OpenShell：现行政策、推理访问与凭证边界分别核对

### 5.1 本章采用的版本与证据

研究日访问的 NVIDIA 文档标为 `Latest (v0.1.7)`；下文按该文档基线描述，而不照搬旧版教程。[来源：NVIDIA Security Best Practices](https://docs.nvidia.com/openshell/security/best-practices)

代码阅读固定到提交 `5d25211b25a8fc887e8d5c606d57d6ab22f1d76c`，对应检索到的 `v0.1.7` 标签对象；具体阅读对象是 `openshell-supervisor-network/src/proxy.rs`。这只是静态交叉核验，并不表示完整读过所有驱动或执行了仓库测试。[来源：NVIDIA 第一方固定提交代码](https://raw.githubusercontent.com/NVIDIA/OpenShell/5d25211b25a8fc887e8d5c606d57d6ab22f1d76c/crates/openshell-supervisor-network/src/proxy.rs)

### 5.2 官方机制：执行政策与可信中介

现行架构把不可信 workload 与可信 supervisor 分离；gateway 管理生命周期、身份、政策与 provider。Linux 工作负载通过 Landlock 限制文件访问、通过 seccomp 与非 root 身份约束进程及网络操作；supervisor 决定请求是否获准、解析 DNS 并提供凭证。[来源：NVIDIA Architecture](https://docs.nvidia.com/openshell/about/architecture)

官方架构描述的外层出口围栏因运行时而异：Docker/Podman 工作负载关闭网络，Kubernetes 仅允许通往 supervisor 的受控路径，VM guest 不配置网络设备并通过认证的 vsock 通道通信。共享政策语义不等于相同的容器／虚拟机隔离强度。[来源：NVIDIA Architecture](https://docs.nvidia.com/openshell/about/architecture)

教学建议：分别验收所选驱动的外层围栏、supervisor 放置位置、宿主或 guest 内核、身份映射及失联处理。不要将“支持多种 runtime”写成“全部模式都有 microVM 边界”，也不要把某个显式代理路径的 namespace 细节推广到所有驱动。

### 5.3 官方机制：配置模式不能视为同等强制

以下差异来自现行官方说明，不是本章的实验结论：

| 维度 | 官方说明的关键差异 | 教学建议：部署判断 |
| --- | --- | --- |
| 连接与请求 | 网络政策检查目的地、端口及调用程序；L7 `audit` 记录规则违反但仍转发，`enforce` 才阻断规则违反。[来源](https://docs.nvidia.com/openshell/security/best-practices) | 不把“默认拒绝未知连接”推导成“已获准连接上的所有违规 API 都被阻断” |
| TLS 可见性 | `tls: skip` 透传，关闭该端点的 L7 检查及占位凭证改写；带 provider 凭证的非检查模式需要显式例外。[来源](https://docs.nvidia.com/openshell/security/best-practices) | 为兼容性开例外时，重新评估可信边界与凭证路径 |
| 文件政策 | 额外文件政策有 `best_effort` / `hard_requirement` 差异；后者也会跳过缺失或无法打开的单独路径，不能理解成“每个配置路径都成功应用”。[来源](https://docs.nvidia.com/openshell/how-it-works/policies/schema) | 检查实际应用／跳过路径，不能只看配置字段 |
| 私网解析 | 精确声明的主机名可能允许解析到私有地址；通配或无主机端点有不同约束，loopback、链路本地与未指定目的地始终阻断。[来源](https://docs.nvidia.com/openshell/security/best-practices) | 不宣称“所有私网永远不可达”；逐项核对有效端点与例外 |

### 5.4 官方机制：推理访问已经不是旧的全局路由模型

现行 Inference 文档明确：workspace-global managed inference route 和 `openshell inference` 命令已移除，客户端改为调用 provider 原生端点。provider instance 管凭证与刷新，profile 管允许的端点与程序，sandbox attachment 决定哪个工作负载获权，客户端管模型、请求格式与超时；attachment 不再选择或改写模型。[来源：NVIDIA Inference](https://docs.nvidia.com/openshell/how-it-works/inference)

工作负载收到不透明占位值，代理仅在网络政策与 profile 端点绑定均通过后替换真实凭证。文档指出旧 managed virtual endpoint 已退休，并要求升级后重建旧 sandbox，避免遗留 supervisor、DNS、信任资料或缓存路由。因此，旧教程中的 `inference.local` 不能作为本章现行部署的默认前提。[来源：NVIDIA Inference](https://docs.nvidia.com/openshell/how-it-works/inference)

教学建议：把三个决策分别验收：请求能否到达目标；凭证能否在该目标使用；该任务是否获准执行这次业务动作。推理请求的提示、文件片段与返回内容仍需数据政策；“真实 API key 不在 workload 内”不表示调用内容不会被发送给服务方。

### 5.5 第一方代码交叉核验到哪里

在固定提交的 `proxy.rs` 中可看到目的地校验调用、受检查的头部凭证改写，以及 `credential_endpoint_mismatch` 返回 403 的处理分支。这支持“目的地与凭证绑定存在不同检查环节”的静态观察，但不足以证明所有协议、重定向、IPv6 和异常路径都正确。[来源：NVIDIA 固定提交 proxy.rs](https://raw.githubusercontent.com/NVIDIA/OpenShell/5d25211b25a8fc887e8d5c606d57d6ab22f1d76c/crates/openshell-supervisor-network/src/proxy.rs)

教学建议：记录实际运行版本、驱动、有效政策和 provider attachment；同时检查外层围栏、L7 enforcement 与上游业务权限。官方架构中的政策证明器以政策变更为检查对象，不能将其描述成对任意运行时、业务流程或提示注入的完整安全证明。[来源：NVIDIA Architecture](https://docs.nvidia.com/openshell/about/architecture)

## 6. 浏览器与 MCP：已连接不等于已授权

### 6.1 教学建议：登录态就是能力，不能跨租户复用

将 Cookie、session token、localStorage、浏览器 profile、下载目录与历史记录都纳入任务状态管理。推荐采用“租户 + 用户 + task”的独立 browser context；不挂载操作者日常使用的个人浏览器 profile，不把已登录 context 放入通用快照。

教学建议：需要登录时，先明确账户主体和站点范围，再引导用户完成授权；对提交表单、发送消息、购买、修改账户等动作单独确认。页面上的文字、按钮标题或 agent 的解释不能代替可信的审批记录。

教学建议：结束任务时销毁 context 并清理下载、缓存与临时存储；若业务必须保留状态，将其作为按租户加密、受访问控制的敏感对象。状态复用必须再次验证身份与任务范围，不能把“之前登录成功”理解为之后任何任务都能使用。

### 6.2 MCP 的工具允许规则不是输出可信证明

OpenShell 现行 schema 明确：MCP 工具规则可限制方法及工具名称，但不匹配工具参数；服务端响应与 server-to-client 消息不在该检查范围内。允许 `tools/call` 或某个工具名，不能证明参数的资源范围正确，也不能证明返回内容可信。[来源：NVIDIA Policy Schema](https://docs.nvidia.com/openshell/how-it-works/policies/schema)

OWASP 对外部内容的分离标记、最小权限和高风险审批建议同样适用于此处的架构分析；协议连接成功不是提示注入防护的证明。[来源：OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)

教学建议：对 MCP 返回值保留服务来源、调用参数摘要与信任标签；对结构、长度、类型及 URI 进行确定性校验。返回的“请执行”“需要补充凭证”“下一步应调用”只能作为不可信数据，不得自动升级为用户指令。

教学建议：工具服务端与业务网关再次验证租户、资源 ID、允许参数和数据范围；不要仅凭工具自称“只读”或名称包含 `read` 判断副作用。读取某个资源的结果也不得自动获得访问其中 URL、路径或其他租户对象的权限。

## 7. 产物导出：设计独立交付闸门

本节是教学建议，不宣称任何产品已经具备完整的安全导出实现。

教学建议：工作负载只能提出“导出清单”，导出服务在独立边界重新检查。将清单绑定当前租户、任务、策略版本及指定接收者；只交付用户明确需要的产物，而非自动同步整个工作区。

建议按以下顺序设计：

1. **范围与文件类型。** 只读取任务专属导出根目录下的允许文件；规范化路径，拒绝目录穿越与根目录外引用。默认只接受普通文件，拒绝设备、socket、FIFO 及未经明确处理的链接对象。
2. **抵抗检查与读取之间的变化。** 由可信服务通过目录句柄和受限文件打开方式读取，校验真实对象，不只做一次字符串前缀判断；必要时先冻结产物目录或复制到隔离交付区。
3. **归档与资源限制。** 检查归档成员路径、链接、嵌套深度、解压总量、压缩比和文件数，不能仅限制压缩文件本身大小。无法安全判断时拒绝自动展开。
4. **格式与内容。** 同时核对声明类型和实际内容；对可执行文件、脚本、Office 宏及 HTML/SVG 等活动内容采用明确的交付政策。秘密扫描和内容检查可以辅助判断，但不能作为“无敏感信息”的保证。
5. **预览与下载分开。** 未信任的活动内容不在控制面同源直接执行；预览转换与扫描也放入受限处理环境。产物默认供下载或受限预览，不自动安装或执行。
6. **交付记录。** 生成包含哈希、大小、内容类型、任务来源与接收主体的清单；下载授权再次检查租户。签名或哈希只能标识来源与完整性，不能替代内容安全判断。

教学建议：把 stdout、截图、浏览器下载、生成报告和工具返回附件都纳入同一数据出口模型。不要因为某条路径不经过网络代理，就允许它绕过交付审批。

## 8. 日志、脱敏与保留：安全事件也有数据边界

本节是教学建议；不声称已验证 OpenShell 或云平台的默认日志脱敏、保留与删除行为。

教学建议：默认记录决策元数据，而非完整提示、请求体和工作区内容。优先字段包括任务与实例标识、策略版本、目标服务、动作类别、允许／拒绝原因、错误码及审批记录引用。URL 查询串、文件名和错误消息也应经过数据分类，不能只过滤 `Authorization`。

教学建议：在日志进入收集器之前，对凭证头、Cookie、API key、JWT、签名 URL、刷新令牌及敏感业务字段进行结构化脱敏；避免命令行调试输出、异常堆栈或 HTTP trace 旁路。禁用真实秘密作为测试数据，也不要将 token 哈希直接当作公开关联 ID。

教学建议：为运行日志、访问日志、浏览器记录、模型 trace 和安全事件分别设置用途、可见角色与保留期。将完整内容调试设为短期、受审批的例外，写明自动到期时间；不提出适用于所有组织的固定天数。

教学建议：保留与删除覆盖索引、对象存储、备份、镜像缓存、快照和第三方遥测接收方。任务销毁只表示计算实例生命周期结束，不能作为这些数据已删除的验收证据。安全事件需保留可调查性，但不能因此无限保留原始秘密。

## 9. 教学建议：上线前要求的证据

下面列的是待执行验收，不是本次研究结果：

- 工作负载、supervisor、控制面与 broker 的放置和权限图；明确任何网络、文件和身份例外。
- 按实际驱动验证默认拒绝、直接连接、双栈解析、地址变化、重定向、代理失联及旧连接行为。
- 用无敏感信息的测试标记验证：未附加 provider、错误端点、过期或撤销任务、跨租户资源及审批后参数变化均被拒绝。
- 同时记录获准操作的成功证据与不获准操作的拒绝证据；单个请求成功不证明不存在旁路。
- 验证 browser context 隔离、快照不带身份、MCP 参数服务端授权、产物路径与归档校验、日志脱敏及保留到期处理。
- 记录镜像摘要、运行时／内核版本、有效政策、证据时间与测试范围；每次升级或兼容例外变更后复验。

教学建议：可以另行引入可信启动、远程证明或机密计算，但其验收应与上述出口和业务授权分开；不能因为增加一种计算环境证明，就删去网络、凭证、工具和数据交付的检查。本章未研究相关证明协议，不作供应商能力判断。
