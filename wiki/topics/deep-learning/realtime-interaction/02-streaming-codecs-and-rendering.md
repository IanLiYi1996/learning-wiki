# 02 流式编解码：时间、token 与延迟是三本账

核查日期：2026-11-09。[专题导读](README.md) · [来源与边界](sources.md)。

## 1. 声音不等于转写文字

音频中包含内容、音色、韵律、停顿与环境音。转写保留了一部分语言内容，但“我没事”的语气和停顿可能丢失。Moshi 的 Mimi codec 用神经编码器、量化和解码器将音频变成较低频率的表示；不同层／码本与语言模型的生成调度共同影响质量和成本。[Moshi 原论文][moshi]

最小阅读路径是：

```text
波形 → 编码器 → 音频表示 → 交互模型 → 输出表示 → 解码器 → 波形
```

其中“表示”可以是离散码、连续向量或多层码本；不能拿一个模型的 token 速率套到另一个模型。[已有语音表示专题](../openmoss/01-audio-representation-and-generation.md)进一步解释残差量化及语义／声学目标。

原创类比：交互模型携带的是简化的“乐谱”，解码器负责把它演奏成声音。压缩越强，乐谱越短，但仍要检验它是否保留任务需要的信息。较少 token 不是更高理解质量的证明。

一个具体对照是 Moshi 论文中的 Mimi 配置：80 ms 一帧，即 12.5 帧／秒；一层语义码加七层声学码，展开后每条流每秒有 100 个码本索引。**帧率不等于展开后的索引率**，也不能把这组数字当作 Higgs 的 codec 配置。[Moshi §3][moshi] · [来源核验](sources.md#moshi)

## 2. 按时间切流，不按完整轮次等待

Boson 使用 160 ms 分块组织并行输入输出，静音也占时间片；推理与工具调用可以跨多个块，工具结果作为输入 payload 到达，并没有固定的每块文字 token 配额。[Boson 时间分块说明][chunks]

用 $\Delta$ 表示物理块时长，可以把第 $k$ 次处理时的已知信息记为 $H_k$，下一输出记为 $O_{k+1}$。因果约束的直觉是：输出只能依据实际已经到达的输入，不提前读取未来用户的改口。

这是抽象接口，不是 Higgs 的公开网络公式。工具耗时 2 秒，不会因为时间片是 160 ms 就在一个时间片内完成；工具结果也不是必须切成等长文字字符串。物理时钟、推理计算和工具事件各有自己的节奏。

## 3. 三个“时间”不要混写

| 时钟 | 计量什么 | 容易犯的错 |
| --- | --- | --- |
| 交互物理时间 | 音频采样、画面到达、说话与播放 | 把块长度当响应时延 |
| 模型生成步数 | token／码本／latent 的调度和计算 | 一步生成不一定占一个播放块 |
| 解码内部步骤 | flow／diffusion 的迭代 | 去噪步数不是对话轮次数 |

Moshi 中的时间与码本深度调度，和 Boson 描述的因果 flow-matching 音频解码／DiT 视频解码，提供了不同层次的例子，不能直接拼成同一架构。[Moshi][moshi] · [Boson 解码说明][renderers]

“因果”不保证零等待。采集需积累数据，前端可能需要 lookahead，模型需要计算，网络与播放缓冲也需要时间。检查某一层是因果的，不能推出整条服务链都是低延迟。

## 4. 怎样计算端到端延迟？

首先定义起止点。例如从“用户完成一条可回答请求”到“用户耳朵听到第一段有用答案”，称为本练习的回答延迟；“好的，我查一下”不计作有用答案。打断停止延迟则是另一个指标。

原创的串行教学账本：

$$
L=W_{\rm capture}+L_{\rm uplink}+L_{\rm queue}
 +L_{\rm model}+L_{\rm decode}+L_{\rm downlink}+W_{\rm playback}.
$$

假设七项分别是 80、25、15、45、20、25、40 ms，合计 **250 ms**。这不是 Higgs 实测。实际流水线会重叠，应该沿事件依赖找到关键路径，不把每个模块的整段耗时机械相加；后台工具结果又可能决定“有用答案”的最早时刻。

如果输入事件在固定长度块内均匀到达，且必须等到块结束才能处理，平均纯对齐等待是 $\Delta/2$，最坏接近 $\Delta$。这个推导依赖均匀到达与整块等待假设，不是任何模型的服务承诺。

## 5. 输入／输出预算为什么要分开？

原创假想配置：块长 160 ms，每块输入 2 个音频单位、输出 3 个，每五块采一帧，每帧 10 个视觉单位，输出画面每块 2 个单位。每分钟有 $60/0.16=375$ 块：

| 流 | 名义单位／分钟 |
| --- | --- |
| 输入音频 | $375\times2=750$ |
| 输出音频 | $375\times3=1125$ |
| 输入视频 | $375/5\times10=750$ |
| 输出画面 | $375\times2=750$ |
| 合计 | **3375** |

这与 Higgs 的具体预算不同，见[案例篇](06-higgs-realtime-duplex.md)。算例只数表示单位；不同模态单位未必有相同计算量、计费权重或 KV 占用，不能把总数直接乘文本 API 单价。

若同一单位率保留最近 4 分钟，名义数量为 **13,500**，还没算文字、工具观察与摘要。静音时继续处理也可能消耗预算。压缩历史能减少增长，但“保留一条摘要”不保证保留精确时间、否定条件或原音细节。

## 6. 声音与脸：内容状态和渲染身份分开

Boson 描述用参考音频与参考图像分别条件化输出解码器，而不是将声线／脸固定写死在前端模型里。[Boson 解码说明][renderers]

从接口设计看，应区分：

- **内容／行为状态**：要说什么、什么时候说、情绪与节奏等。
- **渲染参考**：用什么声线与外观将输出表示解码。

改变参考条件不等于改变推理能力，也不意味着所有身份都可合法使用。因果视频生成还要检验长会话中的连续性、音画同步和错误累积，不能只挑一帧漂亮图片。
