# 05 评测实时助手：答对、时机、任务与风险分别验收

核查日期：2026-11-09。[专题导读](README.md) · [来源与边界](sources.md)。

## 1. 一个分数不能代表整个交互栈

Boson 的评测表横跨 spoken QA、双工行为、视听理解、主动介入、任务完成和文字指令跟随；表内指标、配置与来源不相同。它是厂商汇总和自报，不是本 Wiki 独立重测。[Boson benchmark 表][boson]

原创验收矩阵：

| 层次 | 该测什么 | 单独不能证明什么 |
| --- | --- | --- |
| 听懂／答对 | 语音内容、语境和事实正确率 | 不证明不会抢话 |
| 双工行为 | 附和、打断、让步、旁谈误响应 | 不证明工具真的完成 |
| 视听理解 | 同步输入中的对象、事件与变化 | 不证明主动发声时机正确 |
| 主动介入 | 该提醒时提醒，不该说时不说 | 不证明权限合法 |
| Agent 任务 | 工具、状态、约束与最终完成 | 不证明低尾延迟 |
| 服务体验 | 延迟、稳定性、音画同步、成本 | 不证明内容可信 |

Full-Duplex-Bench 是研究双工交互行为的入口；行为分布、停说／回应时延和韵律各有单位，不能直接与语音识别 WER 或任务成功率混成一个指标。Boson 表里的 “average” 还需还原具体聚合口径，而不是假定它就是原论文全部指标的算术平均。[Full-Duplex-Bench 原论文][fdb] · [Boson 表格][boson]

### 三个基准，三个不同问题

| 基准 | 主要问题与协议 | 关键边界 |
| --- | --- | --- |
| Full-Duplex-Bench v1.5 | 在打断、附和、旁谈与背景语音下，统计行为、停说／回应时延和韵律 | 真正打断期望让步；附和常期望继续，因此停嘴不总是越快越好 |
| τ-Voice | 用语音模拟交互测试工具任务；最终环境状态和必要沟通参与完成判定 | 原始 v1 英语协议与更新的多语言版本不能直接混表 |
| ProactiveVideoQA | 视频开始给出问题，模型自行选择播放过程中的回答时刻 | 有预设问题，不是任意自主行动；PAUC 也不是普通准确率 |

表内定义分别来自 [FDB §2][fdb]、[τ-Voice 原论文][tau]及[ProactiveVideoQA 原论文][proactive]。τ-Voice 当前官方仓库另区分多语言版本，见[版本记录](sources.md#tau-voice-code)；Boson 表中的成绩是否采用哪一版本与条件，仍需其运行配置证明。

PAUC 可以直觉地看成“随时间累积的回答质量曲线”的归一化面积：不仅问最终是否说对，也问什么时候给出了有价值的信息。参数 $\omega$ 控制内容与时机的权衡；原论文的 $\omega=1$ 忽略时机，常用的 0.5 不等于把准确率乘一半。[ProactiveVideoQA 定义][proactive] 下一个小算例只教一对一时窗命中，不实现 PAUC。

## 2. “尽早说”与“说得对”会冲突

原创库存场景：提醒晚了，用户已经走错；提醒太早，候选货架还未核验。理想输出要同时满足有价值、事实正确和时机合适。

一个简化教学任务给出三个该提醒的时间窗 `[1,2]`、`[5,6]`、`[9,10]` 秒。模型在 1.5、1.6、5.5、12 秒说了四次：只有两个时间窗被命中，第二次重复提醒和最后一次窗外提醒均算额外发声。

采用一对一匹配时：

$$
P=2/4=0.5,\qquad R=2/3,\qquad F_1=4/7.
$$

这个原创玩具只测时机覆盖与多说，未验证提醒内容，也不是 ProactiveVideoQA 的 PAUC 实现。语义正确但时间不合适，与时间合适却事实错误，需要在真实评测中分别记录。

## 3. latency 指标先写出起止点

建议至少拆开：

- 接话延迟：用户意图足够明确到第一次听到输出。
- 有用答案延迟：到第一次得到有证据支持的结果。
- 打断停止延迟：从用户打断到旧音频停止。
- 后台完成延迟：从授权发起任务到得到最终回执。
- 音画不同步：同一输出内容在声音和画面上的时间偏差。

上述是本 Wiki 的验收定义建议，不是所有 benchmark 通用定义。“好，我查一下”可以降低接话延迟，却不应降低有用答案延迟。通过 [02 的延迟账本](02-streaming-codecs-and-rendering.md)理解模块贡献，再用真实时间戳测 p50／p95／p99、失败与超时比例。

不要只报告成功请求的平均值；也不要把 160 ms 的分块长度写成整个服务的 p95。

## 4. 任务成功，先定合同

语音 Agent 的评价还涉及用户行为、工具环境和状态演化。相比只测回答文字，验收应追踪当前请求、工具证据和最终状态；Boson 的表将这类能力与 QA 分列。[Boson benchmark 表][boson]

建议冻结下列条件后再比较模型：

| 合同栏 | 需要记录 |
| --- | --- |
| 输入 | 语言、口音、噪声、多人、设备、采样率、视频帧率 |
| 模型／运行 | 版本、thinking 配置、上下文、并发、网络和硬件 |
| 环境 | 工具 schema、数据快照、用户模拟器、超时和失败规则 |
| 指标 | 内容、时机、任务成功、风险、延迟与会话成本分别定义 |
| 数据边界 | 训练反馈、开发集、最终持出集与泄漏检查 |
| 统计 | 样本量、重复次数、置信区间、缺测与失败占比 |

这是原创评测模板。单次成功率 pass@1 与“多次尝试至少一次成功”不同；缺测用横线表示，不是零分。不同推理预算的结果不可无条件归因为架构或参数量。

## 5. 四类安全问题不靠自然语气解决

**持续采集。** 助手不回应旁谈，仍可能接收或保留旁谈内容。明确摄像头／麦克风是否启用、旁人告知、静音和断流是否真正生效、数据保留及删除边界。

**工具与注入。** 屏幕、语音或搜索结果中的“忽略之前指令”是外部内容，不获得控制权限。连续输入增加了入口种类，不能让每个观察都成为执行指令。

**有副作用操作。** 预订、发邮件、改配置、删除与付款需要执行边界和参数绑定；用户中途改口后旧授权不能自动覆盖新参数。见 [03 的状态合同](03-background-reasoning-and-tools.md)和[安全基础的 AI／Agent 章节](../../security/security-101/09-ai-and-agent-security.md)。

**声音／外观身份。** 参考音频和图像的技术可用性不等于本人同意。对可克隆身份的系统，需要授权、使用范围、标识及撤回机制；本读本不提供合规法律结论。

这些是工程检查表，未对某个产品完成安全审计，也未断言其实际违反任何要求。

## 6. 一个最小 PoC，应包含哪些反例？

至少准备以下原创测试：正常轮次、长停顿、简短附和、明确打断、多人旁谈、背景电视、工具乱序、参数改口、权限拒绝、联网失败、长会话摘要后追问。每个案例提前写预期行为，不在看过输出后改评分标准。

只读查询和外部写入分开验收；先在合成／已授权素材及隔离环境中测试。没有额外授权，不启用真实用户录音、真实账户写入或付费模型实验。
